# mehen CLI release notes

The version is printed by `mehen version --json`, with the commit it was built from. Releases are served from `https://mehen.dev/dl/`; `mehen update` installs the latest one.

## Unreleased

### Added

- **`mehen guard install` puts the guard hooks into Cursor and Codex too.** In Cursor, `~/.cursor/hooks.json` gets `beforeShellExecution`, `beforeReadFile`, `preToolUse` for the Write tool and `sessionStart`, each running `mehen hook cursor`; the first three carry `failClosed: true`, so a check that crashes, times out or cannot start blocks the call. In Codex, `~/.codex/hooks.json` (`$CODEX_HOME/hooks.json` when set) gets `PreToolUse` for `Bash` and `apply_patch` and `SessionStart`, each running `mehen hook codex`; Codex runs them once you trust them in `/hooks`, which the install reminds you of (`next` in `--json`). A relative `CODEX_HOME` is read against the working directory, as Codex reads it. Each file is backed up once to `<file>.mehen-backup` and edited in its text, so the person's comments, spacing and order stay; a second install reports `unchanged`, and `--dry-run` writes nothing. A file that does not parse, a `hooks` that is not an object, an event that is not a list, or a Cursor `version` that is not a positive integer is `skipped` with the reason and left byte for byte as it is, as is a file that changes while the install or removal runs. `mehen guard remove` deletes a `hooks.json` only when `<file>.mehen-created` records that Mehen made it and nothing else is in it, and changes nothing in a file that holds no Mehen hook. A result for an agent that is not set up carries `absent: true`, and `--json` carries the `level` in force.
- **`mehen hook cursor` and `mehen hook codex` are the check those hooks run,** with the rules `mehen hook claude-code` uses. Cursor gets `{ permission, user_message, agent_message }` (`beforeReadFile` only `permission` and `user_message`, the fields its schema has), always with a `permission`, and a denial when the input cannot be read. Codex gets Claude Code's shape: `hookSpecificOutput.permissionDecision` `deny` with the reason and a `systemMessage` card, `systemMessage` alone for `warn`, and nothing to allow; when it cannot check the call it exits 2 with the reason on stderr, which Codex reads as a block. In Codex the Bash hook covers file reads too, since Codex reads through its shell, and an `apply_patch` is checked file by file for keys in the lines it adds, not the ones it removes, naming the file that carries the key. Not covered: Cursor's Grep and MCP calls, Codex's MCP and other function tools, and input Codex sends to a running command with `write_stdin`.
- **`mehen doctor` has a `guard` row for each of Claude Code, pi, Cursor and Codex set up on the machine,** from a dry run of `mehen guard install`: `ok` when Mehen's hooks are in place and current, `warn` with `mehen guard install --json` as the next step when they are missing or name another `mehen`, and `warn` with `mehen guard block` when the level is `off`. One `ok` row says when none of them is set up, and the row is `skipped` when `mehen` runs from source. `mehen up` says for each of these agents whether its guard is on, installed at `warn` (`warn only`) or `off` (`guard off`), or why it is not on.

### Changed

- **A second `mehen guard install` leaves Mehen's Claude Code hook where it is in each list** rather than moving it after hooks you added later, so it reports `unchanged`.
- **A hook is Mehen's only when its command is exactly the one `mehen guard install` writes,** in every agent's file: the absolute path to `mehen`, quoted as the install quotes it, then `hook <harness>`. A command that only ends that way, wraps it, adds arguments or adds a shell operator is the person's, and install and remove leave it alone; before, any command ending in `mehen hook <harness>` was taken for Mehen's and removed. Claude Code's settings with a `hooks` that is not an object, or a `PreToolUse` or `SessionStart` that is not a list, are now `skipped` rather than overwritten, and two `mehen guard install` or `remove` runs at once take turns through a lock in the Mehen home.
- **The guard reads shell commands as the shell does, in every agent, and stops what it cannot follow.** It is a guardrail against reading key files by accident through the shell, not a sandbox: interpreters (`python3 -c`, `node -e`) are not inspected. Quotes and backslash escapes are tokenised properly, and `$HOME`, `${HOME}` and a leading `~` are expanded once, as the shell would (`'$HOME/.aws/credentials'` is now a literal relative path). Globs and braces in file names are expanded against the folder within a bound and each match judged (`cat .[e]nv`, `cat *.p12`). It looks past `command` (options only before the program), `builtin`, `env` (`-C` and `-S` modelled, an unknown option stopped), `exec`, `nohup`, `time`, `sudo` (`-D` too), `xargs` (`-a` reads its file) and `NAME=value` prefixes; reads commands inside `$(...)`, backticks, `<(...)`, `sh -c`, `bash -c` and `eval`; stops a shell reading its commands from a here-document, a here-string or a pipe, a command substitution inside `$(( ))`, a function definition, and a command over 65,536 characters or nested over 32 levels. It models `cd` (bare `cd` is HOME), `pushd`, `popd` and subshells, applying a relative `cd` to every folder the line might be in and keeping both folders possible after a `cd` that may not run (after `&&` or `||`, or inside `if`, `while`, `until`, `for` or `case`); `cd -P`, `env -C` and `sudo -D` resolve links on disk; it resolves an existing path on disk before collapsing `..`; judges `ln -s` targets from the link's folder and `ln` targets from the working folder, and a later read of a link made on the same line by its target. A variable or substitution where a file reader takes its file is stopped. So is a relative read after a folder change the guard does not model, when the path could name a key file from some folder. A program that reads files, fed by `xargs` or run by `find -exec`, is allowed only from `find [-H|-P] <start>... <tests> [-print|-print0] | xargs [-0]` or one terminal `-exec`/`-execdir`, with `-name`, `-iname`, `-path`, `-ipath`, `-type f|d|l`, `-maxdepth` and `-mindepth` joined by `-a`: the guard walks the starts within grep's bounds and judges every selected entry as the program would open it, and stops names plain `xargs` would split, a lone `-print0` or `-0`, and anything else. `grep -r` walks the folders it would search, up to 16 deep and 10,000 entries, skipping only `.git`, `node_modules`, `.venv`, `venv` and `__pycache__` (folders only; a folder named on the command line is walked); `-R` follows folder links, stopping only where a folder would be inside itself; `-d recurse` and `--directories=recurse` count as recursive; `--include` and `--exclude` follow GNU grep's last-match-wins rule; a search wider than the bound is stopped with a reason that says to narrow it. A Cursor or Codex hook mehen owns is updated field by field, so a comment inside its entry stays, a comment right after a number or `true` no longer confuses the editor, and `mehen guard install --dry-run` and `remove --dry-run` create no Mehen home and take no lock.

## 0.4.1

A first run on your own machine now goes right from start to finish. After `mehen up`, the local vault is the default vault, so a new enrolment and the links `mehen` checks use it rather than Mehen Cloud. A `mehen up` that times out says to run it again, and plain-text output prints real line breaks. `mehen up --remove` waits until the service has stopped, so it no longer leaves a LaunchAgent that brings the vault back at the next login. The service `mehen up` installs keeps the Mehen home and update choice it ran with. The installer at `https://mehen.dev/install` checks the release manifest's signature before it trusts any checksum in it, and `npx @mehenai/cli up` and `npm create mehen` install and run the same signed `mehen`. A held request in a review group or bundle carries the one code its Review together page shows. `mehen mandate propose` proposes only what this machine asked for in the last 30 days, at low caps and for 30 days, and the vault refuses a proposal for more, with `mandateRefused` saying what to drop. Installed machines update themselves on their next call to the vault once this release is published, or at their next hourly check.

### Added

- **`npx @mehenai/cli up` and `npm create mehen`.** Both run the signed `mehen` from `https://mehen.dev`, installing it with the installer when it is missing; the npm packages carry this release's version and hold no binary of their own.

### Fixed

- **A `mehen up` that times out says to run it again, with the link it was waiting on.** It printed a warning that the vault had returned a link not on `https://app.mehen.dev`, because the local link was checked against Mehen Cloud. It now says "Run `mehen up` again when it is done; it picks up where it stopped." and names the local page in the message (exit 4, `timeout`, as before).
- **After `mehen up`, the local vault is the default vault.** With `local-vault.json` in the Mehen home and `MEHEN_VAULT_URL` unset, a new enrolment, the links mehen checks and the message for an unknown `enr_` id use the local vault, not `https://app.mehen.dev`; `MEHEN_VAULT_URL` and an enrolled workspace still come first. `mehen doctor` names it as the vault a new enrolment uses.
- **Plain-text `mehen up` prints real line breaks,** not `\u000A`, and under the enrolment link the fingerprint's coloured words and the group the page hides, as `mehen enrol` does. `--json` is unchanged.
- **On a Linux desktop without `secret-tool`, `mehen up` and `mehen doctor` say how to move the local vault's key into the login keyring:** install `secret-tool` (`libsecret-tools` on Debian and Ubuntu, `libsecret` on Fedora and Arch), unlock the login keyring and restart the vault (`systemctl --user restart mehen-vault.service`), which then moves the key out of `keys.json`.
- **`mehen up --remove` waits for the service to stop.** On macOS it asked `launchctl` once, straight after `bootout`, while the job was often still stopping, so remove failed and left the LaunchAgent, which brought the vault back at the next login. It now waits up to 10 seconds in all, the stop included and every command held to what is left of that, until launchd says the job is not found or systemd says the unit is inactive, as `mehen up` does between `bootout` and `bootstrap`. A stop that fails, a job still there at the end, or a state query that gets no clear answer (the user bus unreachable, say) keeps the service file and the record and says what to do next, instead of being taken for gone.
- **The systemd user unit no longer waits for `network-online.target`;** the vault answers on loopback only.
- **The vault `mehen up` starts at login uses the same home and update choice.** The LaunchAgent and the systemd user unit now carry `MEHEN_HOME` (the Mehen home `mehen up` ran with, when it is not the default) and `MEHEN_NO_AUTO_UPDATE` when they are set. A value with a line break or other control character is refused rather than written into the service.
- **The enrolment `mehen up` asks for names its workspace.** The ask's `context.workspace` is the workspace's id, slug and name as the local vault's own database has them, where it was null. `mehen enrol` on its own still leaves it null until the slot is verified.
- **The installer checks the release manifest's signature.** `curl -fsSL https://mehen.dev/install | sh` now verifies the manifest's ES256 signature against the release keys compiled into `mehen` (pinned in the script) with `openssl`, before it reads any checksum in it. It then checks the binary's size and SHA-256 against the verified manifest, as before. An unsigned manifest, a signature that does not verify, or a manifest it cannot rebuild byte for byte stops the install with nothing downloaded or changed. The installer now needs `openssl`, which stock macOS (LibreSSL) and the common Linux distributions have; without it, it says how to install it.

### Changed

- **`mehen fetch` says what to ask for when a service rejects the credential.** On a 401, or a 403 whose `WWW-Authenticate` says the scope is too narrow, it prints a `mehen:` hint on stderr, and `--json` (and MCP `vault_fetch`) carry it as `hint`: for a key, the `mehen request` that replaces it; for a connection, the `mehen connect` that reconnects it, with `--scopes` when the service named the scope it wanted. A connection only its platform reconnects (a managed workspace's, or one made with a custom provider) gets a hint that says so and names no command. Each hint names the credential's home (`--home private`, `workspace` or `project --project <id>`) and, for a connection, `--client`; a connection whose OAuth client you may not see gets a hint to reconnect it from its page instead. Any other status carries none.
- **`mehen show` says what an OAuth connection may do:** a `scopes:` line and a `token:` line (when it expires, and whether a renewal is failing and being retried). `--json` and MCP `vault_show` carry it as `connection: { scopes, expiresAt, refreshing, client?, reconnect? }` (`reconnect: "platform"` in a managed workspace), never a token.
- **A reconnect keeps every scope.** `mehen connect --name <existing connection>` reconnects it pinned to the same account and keeps the scopes it holds, adding any `--scopes` asked for; `mehen connect --help` and MCP `vault_connect`'s tool description say so.
- **A dead connection hands over a reconnect link.** When the vault finds a workspace connection needs a person, the refusal's `next` is a reconnect link pinned to its account with `mehen wait <con_id> --timeout 60 --json`, on the failure that kills it and every call after, where the machine may start one; otherwise the connection's page.
- **`mehen request google-service-account` and `github-app` are refused** (`bad_request`, exit 2): minting tokens from either is not built, so nothing could use the key. `mehen request --help` says so, and to an MCP client the vault's own refusal explains it.
- **A Review together page's one code.** A vault that sends one code for a review group or bundle has it printed where the group's link is: `mehen pending` ends a group's line with `; the page shows code K7QM3P`, a held request in a group adds a `group: <url>; the page shows code K7QM3P` line to its block, and `--json` carries it as `group.code` on the ask and `code` on each of `groups`. `mehen plan submit` makes the bundle's code the ask's one check (`{ "label": "code", "value": "K7QM3P" }`) in place of every request's binding code, which each request still carries. A code outside the binding codes' alphabet is dropped, and a vault that sends none gets the old codes check.
- **`mehen mandate propose` and `vault_mandate` `propose` default to what this machine asked for.** Without `--items` or `--classes` (MCP `items`, `classes`), the proposal names the credentials and kinds of this machine's own held requests that carried `mandateCover`, and of what its own mandate let through, in the last 30 days (`GET /v1/mandates/asked`), with `read`; `--days` defaults to 30 rather than 90, and caps to 500 reads, 100 changes, 10 sends and 5 deletes a day rather than 5000, 2000, 50 and 20. With nothing asked for, it refuses at once (`forbidden`, exit 5) and proposes nothing. Against a vault that does not say what was asked for, name `--items` and `--classes`; with more than 200 asked for, choose at most 200 with `--items`. `vault_mandate` advertises only what a machine may propose (credential slugs, up to 30 days, caps up to these defaults), and passes wider values on for the vault to refuse with its reason.
- **The vault refuses a machine's proposal for more than it asked for, or longer or higher than the defaults.** Naming every credential (`--items all`), a credential or a kind besides `read` that this machine has not asked for in the last 30 days, more than 30 days, or a cap above 500 reads, 100 changes, 10 sends or 5 deletes a day is `forbidden` with `mandateRefused` (`items_all`, `item_unasked`, `class_unasked`, `term_too_long`, `caps_too_high`), carried in `--json` and the MCP error; the message says what to drop or lower and `next.command` proposes the same terms cut to what is allowed, with the same `--schedule`, and is left out when there is no valid bounded retry (more than 200 credentials, or an explicit list sharing none with what was asked for). What counts as asked for is what this machine asked for (and a person did not reject) or used under its own mandate, for credentials it can still reach. The person signing may still tick anything, and choose any length and caps, on the sign page. `--days 90` and higher `--caps` are no longer offered to a machine.

## 0.4.0

Mehen runs on your own machine. `mehen up` sets it up in one go: it starts a vault on this machine at `http://localhost:7787` as a service, opens the page where you make your passkey and your workspace, enrols this machine and wires your agents, and run again it picks up where it stopped. `mehen serve` runs the same vault in the foreground, on this machine or, with `--origin`, for other machines to reach over https. `mehen guard` installs guard hooks in Claude Code and pi that stop an agent reading `.env` and other key files or pasting a key into a command or a file, and `mehen hook` is the check they run. The vault engine is the hosted one, unchanged, and a machine can be enrolled in a local vault and Cloud workspaces at once. `mehen mcp` also answers in less: `vault_list` a short row per item a page at a time, `vault_templates` a short entry per template, and a tool list under 34,100 bytes; several result shapes change for MCP clients. Installed machines update themselves on their next call to the vault once this release is published, or at their next hourly check.

### Added

- **`mehen up` sets up Mehen on this machine, from nothing to an agent using keys it never holds.** It starts the vault at `http://localhost:7787` (`--port`, `--data`) as a LaunchAgent on macOS or a systemd user unit on Linux, which start again when you log in, or, where neither is available, as a background process until the machine restarts. It opens the vault's start page, which takes your browser to sign-up with a one-time code that never appears in the command, its output or a log, for your passkey, recovery codes and workspace, enrols this machine under its host name and opens its page, where you type the group of the fingerprint the page hides, then runs `mehen setup` and `mehen guard install` (`--no-agents` skips both). It waits up to 15 minutes for you (`--timeout <seconds>`); run again with no flags, it carries on with the port and data folder it set up, finds what is in place and asks only for what is missing. It says which agents it wired and where the guard is on, and which of them it could not wire. It refuses to use anything on the port that is not the vault in its data folder (exit 1, `conflict`). `--json` writes one object per line: `vault`, `ask` (a link a person must open), `workspace`, `machine`, `agents`, then `done`. `mehen up --remove` stops the vault and removes its service; the data stays. `MEHEN_BROWSER` names the program that opens links (`none` opens nothing), and `MEHEN_SERVICE` picks `launchd`, `systemd` or `process`.
- **`mehen serve` runs a Mehen vault, the hosted engine on Bun with its data in SQLite files under one data folder.** Without `--origin` it answers on this machine's loopback only, at `http://localhost:<port>` (7787 by default), and only to requests addressed to `localhost` or `127.0.0.1`. With `--origin https://<name>` it answers that name only, as the passkeys' site too, behind TLS you put in front of it (Tailscale serve, Caddy); `--bind` changes the address it listens on. It makes its root and seal keys on first start and keeps them sealed by this Mac's Secure Enclave, in the login keyring on a Linux desktop, or otherwise in a file only its user can read; a vault that already holds data never gets new keys, and refuses to start, saying what is missing, rather than make them. Every file it writes is its user's alone, it refuses a data folder anyone else can write, one server at a time may use a data folder, and on Linux it makes itself undumpable. Scheduled work (refreshing OAuth tokens, delayed actions) survives a restart. While it has no account it keeps a one-time sign-up code in the data folder. It keeps a daily dump of each workspace in the data folder, dailies for 35 days and monthlies for a year. `--json` prints `{ origin, data, bootstrap, dumpable, custody }` once it is listening. `MEHEN_SERVE_PORT`, `MEHEN_SERVE_DATA`, `MEHEN_SERVE_ORIGIN` and `MEHEN_SERVE_HOST` stand in for the flags.
- **`mehen guard install` puts guard hooks into the agents that run them.** In Claude Code, a `PreToolUse` hook on Read, Grep, Glob, Bash, Write, Edit, MultiEdit and NotebookEdit and a `SessionStart` note on using the vault, in `~/.claude/settings.json`, backed up once; when Claude Code's sandbox is on, the vault's data folder also goes on its read and write deny lists. In pi, a guard extension in `~/.pi/agent/extensions`, which blocks a call when the check cannot answer. `mehen guard remove` takes out only what it wrote, `--dry-run` shows what either would do, and `mehen guard block`, `warn` or `off` sets what the hooks do (block by default), kept in `guard.json` in the Mehen home; `MEHEN_GUARD` overrides it for one process.
- **`mehen hook claude-code` and `mehen hook check` are the check the hooks run.** They read one tool call as JSON on stdin and deny, warn about or allow reading environment files, `.local-secrets`, key stores, SSH private keys, registry and CLI logins, `~/.aws`, `~/.ssh`, `~/.gnupg`, Mehen's own files and the local vault's data folder, with the agent's tools or with a shell command that reads them, a command that prints the environment or a key variable, `grep -r` over a folder that holds a key file, and a command or a write carrying a private key, a URL with a password or a token that starts like a provider key. The reason the agent reads says what to use instead. `check` takes `{ tool, path, content, command, cwd }` and prints `{ decision, reason, card, findings }`, for any other harness. No vault and no network: it answers in milliseconds.
- **`mehen doctor` says how the local vault's root key is kept** (Secure Enclave, login keyring or a file) and what would protect it better, when this machine set up a local vault with `mehen up`.

### Added

- **`mehen templates new <id> --host <host> --category <category>` starts a provider template,** inside a checkout of the Mehen repository and nowhere else. It writes the template with the safe defaults (an API key bound to exactly those hosts, `Authorization: Bearer {key}` unless `--header` and `--format` say otherwise, reads allowed, every other method held for approval, the `placeholder` ceiling), a test that proves the destination refuses a look-alike host, plain http and, with `--path`, another path, and its entry in the catalogue, then prints the files and the test command. `--path`, `--docs`, `--name` and `--prefix` fill in the rest. It refuses an id that exists or does not match `^[a-z][a-z0-9-]{1,40}$`, a host that is not a plain lower-case DNS name, a docs link that is not https and a reserved header before it writes anything (exit 2; an id that exists is `conflict`, exit 1).

### Changed (MCP)

- **`vault_list` rows are short, and come a page at a time.** Each row is `{ slug, workspace, kind, provider?, account?, status, ceiling, hosts, leaseOnly?, review? }`. `workspace` is now the workspace's id, a string, not the object `{ id, slug, name }`: a client that read `.workspace.slug` gets `undefined`, and finds the slug and name in the answer's `workspaces`, which names each workspace once. Rows no longer carry `accountVerified`, `tags`, `updatedAt`, `lastUsedAt` or `policy`, and leave out `provider` and `account` when they are null; `vault_show` has them. A lease-only credential has `hosts: []` and `leaseOnly: true` instead of its placeholder host. Results come 100 at a time by default (`limit` up to 200, `offset`): a client that ignores `nextOffset` and `total` gets only the first page. `search` keeps the rows whose slug or account contains its text.
- **`vault_templates` with no `id` lists each template as `{ id, title, category, kind, hosts }` and each OAuth provider as `{ id, title, category, clientTemplate, hosts }`,** not the catalogue `mehen templates --json` prints: `categories`, `redirectUri`, `displayName` (now `title`), each entry's `policySummary` and its other fields come only with `id`, which still returns one entry in full.
- **A successful result's text is compact JSON,** one line instead of indented.
- **An error's step a tool does is `next.tool` and `next.arguments`, and loses `next.command`.** `mehen wait apr_1` becomes `{ "tool": "vault_wait", "arguments": { "id": "apr_1" } }`, and arguments with a placeholder such as `<mdt_id>` are partial. `next.say` stays a sentence for the human; a `mehen ...` in backticks in it, or a flag outside one, is named as the tools have it (`vault_list`, `client`, `timeoutSeconds`), while a command written in plain prose keeps its words and flags. A usage error and the vault's own `bad_request` point at the tool's input schema. A step only the command line takes keeps `next.command` and has no `next.tool`.
- **Every tool has a `title` and `annotations`, and six an `outputSchema`.** Read-only tools carry `readOnlyHint` and `openWorldHint` only, since `destructiveHint` and `idempotentHint` apply only to tools that act; `vault_request` and `vault_connect` are not idempotent, since `new: true` makes a new link every time. Shorter descriptions bring the tool list to under 34,100 bytes.

## 0.3.19

A machine, watched or not, can ask its owner for a mandate with `mehen mandate propose`: once they sign it with their passkey, its held requests of the kinds it names go through without asking, within daily caps, until a date and optionally only in certain hours. `mehen mandate ls`, `show` and `uses` say what it may do and what went through on trust, `mehen mandate pause` stops it at once, and a request held for approval says when a mandate could have let it through. The machine never signs, resumes or stops one. Installed machines update themselves on their next call to the vault once this release is published, or at their next hourly check. The vault switches mandates on workspace by workspace; where they are off, every mandate command says so in one line.

### Added

- **`mehen mandate propose --note <text>` asks for a mandate and prints the sign page to hand over (exit 0).** `--items all|<slug>,...`, `--classes read,change,send,delete` (read is always included), `--days 1|7|30|90`, `--caps send=50,...` and `--schedule "Europe/Paris mon-fri 08:00-19:00; sat 10:00-14:00"` name the terms, with every credential, all four classes, 90 days, the protocol's daily caps and any hour as defaults; terms the vault would refuse are refused before anything is sent (exit 2). The person signing may change any of them. Nothing waits on the ask, so it has no `mehen wait` and stays out of `mehen pending`; `mehen mandate ls` shows it again while it is open.
- **`mehen mandate ls`, `mehen mandate show <mdt_id>`, `mehen mandate uses <mdt_id> [--since 1h]` and `mehen mandate pause [<mdt_id>]`.** ls and show print the machine's own view: state, what it may do, today's counts against the caps (UTC), the hours and the end; a paused or tripped mandate says the person who signed it can resume it from the mandate page. uses follows the vault's pages to the end, or back to `--since`. pause sends the revision it read, and leaves one already paused or tripped alone.
- **MCP `vault_mandate { action: propose | list | show | uses | pause }`** does the same for an agent; `propose` hands over the ask with a `then:` pointing at `list`, and `uses` returns at most 500 receipts at a time, with `truncated` and `next` to pass back as `before`.
- **`mehen fetch` and `vault_fetch` say when this machine's mandate let a request through:** `allowed without asking by this machine's mandate mdt_...` on stderr and `mandate` in `--json`, beside `rules` and `postures`. A request held because a cap was reached says which caps in its message ("This machine's mandate has used today's 50 sends."), with `mandate` `{ id, capped }` in `--json`.
- **`mehen mandate ls` and `vault_mandate list` show this machine's open proposals first,** each as `Waiting for its signer: <url>, proposed <date>, expires <date>: <reason>`, with `proposals` in `--json`. Proposing the same terms and reason while they wait hands back the same link with `existing: true` (exit 0), and the refusal at 3 open proposals carries the newest one's link and says `mehen mandate ls` (`vault_mandate list` under MCP) lists every open one, or warns when the vault's link is not its own.
- **A paused, tripped or ended mandate links its own page.** `mehen mandate show`, `ls` and the refusal to pause one already ended print the mandate page, `/w/<slug>/mandates/<mdt_id>`, and carry it in `next.url`, checked against this vault as every link is; an active one reads `Active: covers what it names while the person who signed it still stands behind it.`
- **`mehen mandate show` says which proposal a mandate was signed from,** `Signed from proposal mdp_...`, with `proposal` in `--json` and `vault_mandate` when the vault names one.

## 0.3.0

Many workspaces on one machine without bending anything, an enrolment that cannot deadlock, and a CLI that checks for signed releases and installs them itself. Installed release builds with a compiled trusted release key check for signed updates automatically; a build with no trusted key updates nothing.

**Getting there from 0.2.0.** Run `mehen update --json` once on each machine. A 0.2.0 `mehen` cannot check a release signature, so this one update is checked against the manifest's hashes over TLS only; every update after it is signed, and a release build with a compiled trusted key checks for them automatically from then on. Do not run the installer on a machine that already has `mehen`. The first non-observational 0.3.0 command that uses slots migrates `~/.config/mehen` in place (below); `mehen workspace list` is the local-only migration command; nothing needs re-enrolling, and credentials and projects are untouched.

### Breaking changes

- **One state directory, one slot per workspace.** Workspace identity state lives under `MEHEN_HOME` (default `~/.config/mehen`); harness registrations and skill ownership remain per OS user, and update state is beside the executable: `workspaces/<vault>/<tn_id>/` for each active workspace and `pending/<vault>/<slug>/` while an enrolment waits. The 0.2.0 layout (the first enrolment in `~/.config/mehen` itself, the next ones in `contexts/<slug>`) is migrated by a slot-using command such as `mehen workspace list`, under a journal (`migration.json`) that resumes after a kill; device state is retained, while obsolete update-check files and the completed journal are removed. A directory that is not a slot (a hand-made `revoked-*`, say) is named by `mehen doctor` and left alone. A managed host is never migrated automatically: its owner provisions the pinned slot first.
- **`MEHEN_CONFIG_DIR` is retired to an alias.** For 0.3.0 it is read as `MEHEN_HOME` when it names the root, and refused as `config_dir_retired` (exit 2), before anything is read or sent, when it names a slot, a pending slot, an old context directory, or disagrees with `MEHEN_HOME`; the refusal names the `MEHEN_HOME` to use. The alias goes in the next release: move launchers and MCP entries to `MEHEN_HOME`. On a managed host the pinned slot directory is still passed as before.
- **`mehen enrol` prints the ask and exits 0.** It no longer waits in the foreground or needs to be backgrounded: relay the link, then `mehen wait enr_...` finishes the enrolment, from any shell. `--wait` keeps the old behaviour. Running `enrol` again resumes the same attempt with the same key; on an active workspace it answers `active` and changes nothing.
- **Links stay alive in place.** An attempt's link lives 60 minutes and `mehen wait` renews it while it waits (same id, address and fingerprint), up to 24 hours; there is no "issue a fresh link up to three times" any more. Only a terminal `expired` means a new attempt (`mehen enrol` again). A 0.2.0 attempt migrated as pending is never renewed and expires at its old time.
- **No default workspace.** `mehen workspace default` is gone. A command that needs one workspace takes `--workspace`, `MEHEN_WORKSPACE` or the checkout's `mehen.toml`, else the only workspace there is; several and nothing deciding is `context_ambiguous`. `status`, `doctor`, `ls`, `pending` and `workspace list` cover every workspace.
- **`mehen status --json` lists every workspace**: `{ home, allowed, workspaces, selected, next, cli }`, each entry `active` (with a `check` from the vault that never deletes anything), `pending`, `corrupt` or `absent`. `mehen status --workspace <slug> --json` keeps a scalar one-workspace result but renames `context` to `slot`. `mehen doctor --json` is one report for the machine, each vault and each workspace, with `cli`, `migration` and `strays`. `vault_status` and `vault_doctor` return the same shapes; `vault_status` has no `enrolled` field any more.
- **Status is observational.** `mehen status` and `mehen whoami` neither migrate the root nor persist display-field changes; `mehen workspace list --check` records a renamed workspace's new slug and name (only those, and only for the slot's own workspace and origin). On a legacy or resumable root they refuse with the next command to run; `mehen workspace list` performs the local migration, then status can be retried. `mehen doctor` reports the journal without migrating it.
- **Listings span workspaces.** `mehen ls` and `vault_list` add `workspace` to each item, and CLI tables add a workspace column when results span more than one workspace. A slug is unique only within its workspace: pass `--workspace` or the MCP `workspace` argument on subsequent single-item operations. Aggregate pending lists also span the admitted workspaces; a singular selector limits the applicable commands.
- **One MCP server for every workspace.** `mehen mcp` serves every workspace the entry's `MEHEN_WORKSPACES` allows, including one enrolled while it runs; every tool except `vault_templates` takes `workspace` (slug or id), needed only when more than one could serve. Each workspace is latched to the identity it first served; one whose enrolment changes under the server is refused until the agent restarts, while the others keep serving. `mehen setup --workspace` and the `mehen-<slug>` servers are gone: the next `mehen setup` removes the old `mehen-<slug>` entries it wrote and reports them under `removed`.
- **`mehen update --json`** answers `{ current, latest, available, updated, path, result, skills? }` with `result` one of `updated`, `current`, `locked`, `held` or `rolled_back`, and `skills` the per-skill report instead of `"refreshed"`.
- **The installer is for a fresh machine only.** On a machine with a verified `mehen` it prints `Already installed`, downloads nothing and changes nothing unless `--force` (a human's decision, for example after losing the only release key). Its last line is now `mehen-install: {"v":1,"result":...,"version":...,"path":...,"onPath":...,"env":...,"rc":{...}}`. It writes one guarded PATH line for zsh and bash and gives advice for other shells, and never overwrites a file it does not own.
- **A wider refusal when the user's home cannot be resolved.** The managed-host marker is now read under the home directory the system's user database records for this uid (`getent passwd`, then `/etc/passwd`, on Linux; `dscacheutil` on macOS), never under `HOME`. When that lookup fails or answers something unsafe (a relative path, a symlinked or group- or world-writable component, a home not owned by this uid), state-opening commands fail closed with `key_insecure` (exit 6) instead of guessing (pure help, guide and version output does not open the managed marker), naming the uid and the fix. Only a definite "no such user" on a Linux host whose user database is the plain files is treated as unmanaged. `HOME` and `MEHEN_HOME` no longer move where the marker is read.

### New

- **`MEHEN_WORKSPACES`**: a comma-separated list of slugs, `tn_` ids or `<vault>/<slug>` that this process may use. It only narrows; anything outside is `workspace_not_allowed` (exit 2), and nothing inside a process widens it. An allowed workspace not joined yet shows as `absent` with the enrolment to run.
- **`mehen setup`** writes one `mehen` entry per agent and carries the shell's `MEHEN_WORKSPACES` into it whenever it is restricted (and `MEHEN_HOME` when not the default), so a restricted shell never writes an unrestricted server. `--workspaces a,b` requests a narrower entry and refuses a request wider than the calling shell; an existing wider entry is skipped until `--reset-env` rebuilds its environment. `--mcp-file <path>` writes `mcpServers.mehen` into any compatible JSON MCP client's file; use `--agent vscode` or `--agent opencode` for those clients' different formats. `--print [--format json|toml]` prints the entry and writes nothing. `--reset-env` rebuilds an entry's `env`, for one that still carries `MEHEN_CONFIG_DIR`. A `mehen` entry made by hand, or edited by hand after setup, is `skipped` with its reason until `--force` takes it over, still under every env check. Each agent reports `mcp` as `added`, `updated`, `unchanged`, `skipped` or `failed`, and each skill as `added`, `updated`, `unchanged`, `removed`, `external` or `failed`; setup exits 1 on any `failed`. `--remove --agent X` keeps the skills while another entry remains.
- **`mehen enrol --connect <code>`**: a connect code from the workspace's Connect an agent page claims the attempt for that member, so it lands in their own Needs you and only they can accept it. A refused code is `forbidden` (exit 5).
- **`mehen workspace forget (<slug or id> | --slot <path>)`** retires one slot on this machine only, without the vault; the device stays on the Machines page until someone revokes it there.
- **Self-update.** Releases are signed with a Secure Enclave release key whose public half is compiled into the binary. Installed release builds with a compiled trusted release key check for signed updates automatically; a build with no trusted key updates nothing. With a key, `mehen` checks for a release about every six hours in the background after a command and installs only a signed, newer version, with one journalled rename next to the binary. `mehen update` does it now; `--version <v>` selects a named signed release, while an intentional downgrade needs `--force` or a verified `--rollback`. Those local overrides still verify the release signature. `MEHEN_NO_AUTO_UPDATE=1` or `autoUpdate: false` in `settings.json` under `MEHEN_HOME` turns it off; CI and source runs never update themselves. After an update the command line uses the new version at once, and a running `mehen mcp` says in a tool result (and in `cli.mcp` of `vault_status`) that the agent should restart to load it.
- **`cli_outdated`** (exit 1): the vault refuses a `mehen` below its minimum version (HTTP 426) everywhere but freeze and self-revoke. `mehen` updates itself before a command when it knows the minimum is above it, and a refusal in the middle of a command is shown once with the command to run again, never re-run. Every `/v1` answer carries `Mehen-Cli: minimum=<v>` (with `; recommended=<v>` when the vault sets one), and requests send `User-Agent: mehen/<version>`.
- **`mehen doctor`** gains `home`, `migration`, `on_path` and `update` rows, checks every workspace, and never migrates, writes or deletes anything.
- **The docs moved to https://docs.mehen.dev.** The setup guide lives at https://docs.mehen.dev/setup.md and the skill at https://docs.mehen.dev/skill.md; the old addresses on `mehen.dev` redirect. `mehen guide` and the skill name the new address.
- **`mehen version --json`** adds `build` (`release`, `dev` or null when running from source) and `helper` (`embedded` or `none`); `commit` is also null for a source run without a build stamp. On macOS the Secure Enclave helper is embedded in the binary and extracted under `MEHEN_HOME/bin` on first use; the separate `mehen-se` file a 0.2.0 install left beside the binary is removed by the first update that 0.3.0 itself installs, when it and its checksum file match.

### Fixed

- Finishing the same enrolment from two processes (a backgrounded `enrol` and a `wait`) no longer revokes the device it just activated: the same key finishing twice is one success. Two different devices approved for one workspace on one machine is `already_enrolled`, which now revokes and deletes nothing and says how to keep one.
- `mehen revoke` removes a slot only when the vault revoked it or says it was revoked already, so "already enrolled, revoke first" and "revoked, enrol again" can no longer point at each other; `mehen enrol` on a revoked slot starts a fresh attempt.
- Locks per slot stop two enrolments committing a key and a config that do not match.
- An approval granted just before a link's local expiry is no longer stranded: the record is kept until the vault says the attempt is over.
- `mehen update` no longer reports skills as refreshed when some were left alone.

## 0.2.0

Workspaces. The vault now holds many workspaces, each with its own members, teams, projects, credentials, machines and audit, and every machine is enrolled in exactly one of them.

**Enrolments made with 0.1.0 stop working at the cutover.** The vault's data starts fresh: every machine enrolled by 0.1.0, every credential and every project is gone, and a 0.1.0 `mehen` cannot enrol against the new vault (its enrolment names no workspace). Update (`mehen update --json`, or `curl -fsSL https://mehen.dev/install | sh`), then enrol again with `mehen enrol --workspace <slug>`. The update keeps the old enrolment's files in `~/.config/mehen`, so the new enrolment lands in `~/.config/mehen/contexts/<slug>`: make it the default with `mehen workspace default <slug>` (which also decides what the plain `mehen` MCP server serves), verify with `mehen status --json`, and let the human delete the dead enrolment's `config.json`, `device-key*` and `ledger.json` from `~/.config/mehen`; `https://mehen.dev/setup.md` has the steps. This is forward only: a 0.1.0 `mehen` cannot be used against the new vault, so there is no downgrade. The human re-adds credentials through intake links and re-creates projects with `mehen init`.

- **Workspace enrolment.** `mehen enrol --workspace <slug>` is required; a bare `mehen enrol` is a usage error (exit 2) and sends nothing. The slug is on the workspace's Connect an agent page. The machine's owner accepts it with their passkey; `--team <team-slug>` enrols a machine a team owns, which an owner or admin admits. The enrolment is verified against what was asked for before anything is written: an activation in another workspace, with another owner kind or without a complete scope writes no config: the CLI attempts to revoke the new device, reports whether that succeeded and, when it did not, names the device for a human to revoke. One enrolment per workspace per machine: the first lives in `~/.config/mehen`, the next in `~/.config/mehen/contexts/<slug>`, or wherever `MEHEN_CONFIG_DIR` points. Keys are scoped to one workspace and never reused across workspaces.
- **Contexts and selection.** A context is picked before any signature: `MEHEN_CONFIG_DIR`, then `--workspace <slug or id>` (a global flag) or `MEHEN_WORKSPACE`, then the checkout's `mehen.toml` (`workspace` and `vault`), then the default. New command `mehen workspace list [--check] | show | default <slug or id> | bind`. New local refusals, all exit 2 and never from the vault: `workspace_unknown`, `workspace_mismatch` (also for a `MEHEN_VAULT_URL` or key scope naming another origin or workspace), `context_ambiguous`, `workspace_unbound`. `mehen status` and `vault_status` name the workspace (id, slug, name), the owner and the context directory; every status call refreshes the recorded slug and name from the vault, never the id. `mehen revoke` revokes only the selected context.
- **Managed-host pins.** A managed host's agent configuration must be current. An outdated one is refused as `pin_outdated` (exit 2): selection fails closed, nothing is inferred, and only the harness owner can repair it. On a managed host only the pinned `MEHEN_CONFIG_DIR` is accepted.
- **Private credentials and homes.** `mehen request` and `mehen connect` take `--home private|project|workspace` (`--project <prj_id>` for a project home, or the checkout's manifest project); `vault_request` and `vault_connect` take `home` and `project`. The default is `private`: only the human who fills it in can use it, through their own machines with the private-credentials tick. The human may change the home on the page.
- **Overrides in `env ls`.** A member may set a personal override for a variable in an unprotected environment on the project page (their own private credential, or a plain non-secret value). `mehen env ls` marks it `override (your <slug>)` or `override (your plain value)` in its text and `override: true` in `--json`; `mehen env check --json` carries the same marker, while its human output only reports whether every variable resolves; `mehen run` names overridden variables in its banner. No value is ever printed.
- **Project context for `fetch`.** `mehen fetch --project <prj_id> --env <name>` and `vault_fetch` `context: { project, environment }` name the project environment a credential is used for, which a protected credential requires, and so does a workspace credential that a team's or a guest's machine reaches through a shared project; a credential whose home is a project you may use, or your own private one, is reachable by name. A context is an extra requirement, not a default: the environment must reference a non-private credential, and a private one needs an authorised unprotected environment. It never changes the workspace.
- **Links under the workspace.** Every ask link is `https://<vault>/w/<slug>/...`, under the canonical slug of the workspace the machine is enrolled in. A link under another slug, an alias or another origin is refused and rebuilt from the id under the canonical slug, with a warning; a link cannot be trusted without a known slug. Asks carry `context: { origin, workspace: { id, slug, name } | null, device }`, the enrolment that raised them.
- **The identity gate.** A workspace may require a verified Google identity on its domain. The vault then refuses a human who has not signed in with Google recently with `identity_required` (exit 4): the human completes the sign-in in the workspace, and the agent repeats the step. Google only identifies; passkeys still authenticate and sign. Enrolled machines are not re-gated in this release; removing a member cuts their machines off at once. New codes `account_pending`, `owner_inactive` and `project_unshared` are exit 4 as well.
- **MCP.** One `mehen mcp [--workspace <slug or id>]` server binds one context for its lifetime and refuses to serve anything else; `vault_env` in a checkout of another workspace is `workspace_mismatch` ("start a second server"). `mehen setup --workspace <slug or id>` registers that workspace's server by its stable id, as `mehen` for the default context or `mehen-<slug>` for another, without touching other registrations; `mehen setup` with no flags writes exactly what 0.1.0 wrote. Tool names are unchanged. `mehen pending` and `vault_pending` show this machine's own asks and its own "machine added" notice only.
- **Policy proposals** (`mehen policy preview|propose`, `vault_policy`) keep their surface but are refused by the vault in this release (`forbidden`, "Policy widening is not available yet"); `show`, `cancel` and `stop` work.
- **Help and next steps** from the CLI itself name `--workspace <slug>` wherever they tell you to enrol (the vault's own `next` for an unknown or revoked machine still says `mehen enrol`; add the workspace), and use neutral example names.
