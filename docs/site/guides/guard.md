# The guard hooks

The vault keeps keys out of an agent's hands when the agent goes through Mehen. The guard hooks cover the other way a key reaches a model: the agent reading a `.env` file, a key file or a CLI's login, or pasting a key it found into a command or a file. Before each tool call, the agent's harness asks `mehen hook` about it. The guard blocks the call, or warns about it, and tells the agent what to use instead.

The guard is not the security boundary: the vault's bindings are. It keeps an agent from handling a key by accident, or because a page or a file told it to, and it reads nothing but the paths and text in the tool call. It needs no vault and no network, so it answers in milliseconds and works with a local vault, another machine's or Cloud.

## Install it

`mehen up` installs it. To install it on its own, or again after you install an agent:

```sh
mehen guard install --dry-run
mehen guard install
```

It needs an installed `mehen`, since the hooks name its path. For each agent it reports `added`, `updated`, `unchanged` or `skipped` with the reason. Restart the agent afterwards (in pi, `/reload` is enough; Cursor picks up its file by itself).

- **Claude Code.** It adds a `PreToolUse` hook for Read, Grep, Glob, Bash, Write, Edit, MultiEdit and NotebookEdit, and a `SessionStart` hook that tells the agent how to use the vault, to `~/.claude/settings.json`. The file is backed up once, to `settings.json.mehen-backup`, before the first change. It is skipped when there is no `~/.claude` folder.
- **pi.** It writes a guard extension into `~/.pi/agent/extensions`, which pi loads by itself. It checks bash, read, grep, find, ls, write and edit. If `mehen hook check` fails, the extension blocks the call rather than let it through unseen; if `mehen` is no longer installed at all, it says so once and stops guarding. It is skipped when there is no `~/.pi` folder, and a file of the same name that `mehen` did not write is left alone.
- **Cursor.** It adds four hooks to `~/.cursor/hooks.json`, each running `mehen hook cursor`: `beforeShellExecution` checks every shell command, `beforeReadFile` every file the agent is about to read, `preToolUse` the Write tool's input, and `sessionStart` tells the agent how to use the vault. The shell, read and write hooks carry `failClosed: true`, so a crash, a timeout or a missing `mehen` blocks the call instead of letting it through. Cursor reloads the file by itself. It is skipped when there is no `~/.cursor` folder.
- **Codex.** It adds a `PreToolUse` hook for `Bash` and `apply_patch` and a `SessionStart` hook to `~/.codex/hooks.json` (`$CODEX_HOME/hooks.json` when `CODEX_HOME` is set), each running `mehen hook codex`. Codex reads files through its shell, so the Bash hook covers reads as well as commands; the `apply_patch` hook checks the lines a patch adds. Codex runs a new or changed hook only after you trust it: open `/hooks` in Codex and trust Mehen's two hooks after the first install, and again whenever `mehen guard install` reports `updated`. It is skipped when there is no `~/.codex` folder.

Each file is backed up once, to `<file>.mehen-backup`, before Mehen first changes it, and written only when something changes, so running the install again reports `unchanged`. A hook is Mehen's only while its command is exactly what the install writes: the absolute path to `mehen`, quoted as the install quotes it, then `hook <harness>`. Anything else is yours and is never touched, including a command that merely ends that way (`/bin/echo /opt/mehen hook cursor`), wraps it (`env ... mehen hook cursor`), adds arguments or adds a shell operator. In Cursor's and Codex's `hooks.json`, only Mehen's entries are edited in the text, so your comments, spacing and order stay as you wrote them; when `mehen` moves, only the fields Mehen writes in its own entries change, so a comment you put inside one stays too. `--dry-run` only reads: it creates no Mehen home and takes no lock. A file that does not parse, a `hooks` that is not an object, an event that is not a list, or a Cursor `version` that is not a positive integer is reported with the reason and left byte for byte as it is. A file that changes while the install or removal runs is left as you changed it, and reported. Two `mehen guard install` or `remove` runs at once take turns, through a lock in the Mehen home.

`mehen guard remove` takes out only what `mehen guard install` wrote. A `hooks.json` that Mehen created is recorded beside it, in `hooks.json.mehen-created`, and only that record lets the removal delete the file, once nothing of yours is in it. A file you had before keeps everything but Mehen's entries, and a file with no Mehen hook in it is never changed.

`mehen doctor` has a `guard` row for each of these agents set up on the machine: on, missing, out of date (it names another path to `mehen`), or off because of the level. `mehen up` says the same for each agent it wires: `guard on`, `guard installed, warn only`, `guard installed, guard off`, or why the guard is not on.

## What it stops

**Reading a file that holds keys**, with the agent's read tools or with a shell command that reads its arguments (`cat`, `grep`, `head`, `sed`, `cp`, `curl`, `git`, a `<` redirect and others):

- environment files: `.env`, `.env.*`, `*.env`, `.dev.vars` and `.envrc`, but not examples such as `.env.example`;
- anything in a `.local-secrets` folder;
- key and certificate stores (`.pem`, `.key`, `.p12`, `.pfx`, `.jks`, `.keystore`, `.ppk`, `.kdbx`) and SSH private keys (`id_ed25519` and the like; a `.pub` is fine);
- `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `.pgpass` and `.my.cnf`;
- CLI logins: `gh`, kubeconfig, talosconfig, the gcloud application default credentials, the Cloudflare command line's and Docker's;
- anything under `~/.aws`, `~/.ssh`, `~/.gnupg`, Mehen's own `~/.config/mehen`, and the local vault's data folder.

**How it reads a shell command.** The guard is a guardrail against an agent reading a key file by accident, or because a page or a file told it to, through the shell. It is not a sandbox. It reads the command line and nothing else: an agent that runs an interpreter (`python3 -c 'open(".env").read()'`, `node -e`, a script it wrote) is not inspected, and a program determined to read a file can always disguise it. Mehen's protection is that agents never hold keys: the vault makes the call with the key, and the agent sees a placeholder.

The guard follows a fixed part of the shell's grammar, exactly:

- simple commands with their redirections, joined by pipes, `;`, `&&`, `||` and `&` (a list run in the background with `&`, such as `cd /tmp && true &`, runs in a subshell, so it leaves this shell where the list began);
- single and double quotes and backslash escapes;
- `$VAR` and `${VAR}` with no operator; `$(...)`, backticks and process substitution `<(...)` and `>(...)`, whose commands are read too (a `cd` inside a process substitution ends with it);
- `cd`, `pushd` and `popd` in the main shell;
- globs using `*`, `?` and plain `[...]` sets and ranges, and brace expansions such as `{a,b}` and `{1..3}`;
- here-documents given to a program as data;
- the `time` keyword before a command that is not one of the builtins that change this shell (`cd`, `pushd`, `popd`, `source`, `.`, `exec`, `eval`, `export`, `set`, `shopt`, `alias`, `unset`): the command is judged as if `time` were not there;
- the wrappers below, up to 8 in a row, and the one form of `find` described below;
- for each program the guard reads (`cat`, `head`, `tail`, `grep`, `sort`, `uniq`, `cut`, `diff`, `cmp`, `od`, `hexdump`, `base64`, `strings`, `tr`, `cp`, `sed`, `awk`, `jq`, `cd`, `pushd`, `popd`, the shells, the wrappers), the options it understands, from each program's manual: whether each takes a value, and whether that value is a file the program reads (`grep -f`, `sort --files0-from`, `sed -f`, `awk -f`, `jq --rawfile`, `bash --rcfile`), which is then judged like any read. An option not on a program's list is outside the grammar. Programs whose options are too many to list (`git`, `curl`, `wget`, `rsync`, `tar`, editors, interpreters) have every word judged as a possible file instead: the word, the value after an `=`, a value attached to a short option, and each without a leading `@`, each expanded as the shell would expand its globs and braces, so `curl -d @.env`, `curl -T .env`, `wget -i .env`, `rsync --files-from=.env`, `git -c include.path=.env` and `git diff --no-index /dev/null .[e]nv` are found. A word whose value only the shell knows is not judged for these programs, because it is as often a message or a branch name as a file: `git diff --no-index /dev/null "$F"` with `F=.env` reaches `.env` unchecked. Options whose arity differs between the GNU and BSD versions of a program (`sed -l` and `cp -S` take a value in GNU and none on macOS) are left off its list, and `+NUM` is always judged as a file (`head +123`).

**The rule.** When a command line uses anything outside that grammar, and anything on the line reads a file or prints the environment, the guard stops it: "can't tell what this reads; run the read on its own". Reading means a program that reads files (or, on a line outside the grammar, any word anywhere that names one, names a key file, or expands a key variable, since the guard cannot then tell which words are commands) (`cat`, `grep`, `head`, `git`, `bun` and the like), a file given to a shell or an interpreter to run, input redirected from a file, `grep -r`, `find` feeding a program that reads, or `env`, `printenv`, `set` or `export -p` printing the environment. A line that uses something outside the grammar but reads nothing passes, so `for f in *.ts; do echo $f; done` is fine and `for i in 1 2; do cd ..; done; cat x` is stopped.

Outside the grammar: an option a modelled program does not list, loops and conditionals (`for`, `while`, `until`, `if`, `case`, `select`), `{ ...; }` groups, `[[ ]]`, `!`, functions, subshells `( ... )`, a `cd` inside a subshell, a `$(...)` or a pipeline, `${...}` with any operator, arithmetic (`$(( ))`, `$[ ]`, `(( ))` wherever a command starts, `for ((...))`, `let` and integer variables made with `declare -i`, which read variables by bare name; `((` or `$((` that bash would not read as arithmetic is read as the subshells bash runs instead), `declare -n` name references, `$'...'` and `$"..."` quoting, here-strings, coprocesses, aliases, `eval`, `source` and `.`, `exec`, the `time` keyword before one of those builtins, or alone (a `time` program named by its path, such as `/usr/bin/time`, is a wrapper), `shopt`, `set -o`, `set +o` and `set -f`, a numeric brace sequence with a zero-padded end (`{01..03}`) or ends past 100,000, `bash -O`, `+O`, `-o` and `+o`, assignments to `HOME`, `IFS`, `GLOBIGNORE`, `PATH`, `CDPATH`, `BASH_ENV`, `ENV`, `BASHOPTS` or `SHELLOPTS`, POSIX classes such as `[[:alpha:]]` in a glob, and extended globs. A few of these can run a command the guard cannot see, or print a key, and are stopped even with no read on the line: a read through another variable, `${!v}` (or `${!1}`, `${!#}`) with or without an operator or a `declare -n` name reference, whose variable the guard cannot name (a `${!v}` anywhere in the command's text counts, even in single quotes or a quoted here-document; `${!prefix*}` and `${!array[@]}`, which list names, and `${!}`, a process id, pass), an unquoted here-document or a here-string that expands a key variable (`cat <<EOF` then `$OPENAI_API_KEY`), arithmetic that reads one by name (`$((OPENAI_API_KEY))`), an alias, a coprocess, `eval` of a word only the shell knows, a `${...}` or `$(( ))` holding a command substitution, an unquoted here-document that runs one, and a line too long (over 65,536 characters) or too deeply nested (over 32 levels) to read. More than 8 wrappers in a row is stopped too.

Within the grammar:

- Line continuations (a backslash before a newline) are removed first, as bash removes them, except inside single quotes, in a comment and in a quoted here-document's body, so `echo $\` then `OPENAI_API_KEY` on the next line is `echo $OPENAI_API_KEY`.
- Quotes and backslashes are read as the shell reads them: `/home/a/.a\ws/credentials` is `.aws`, and `my\ .env` is one file. `$HOME`, `${HOME}` and a leading `~` are your home folder, so `'$HOME/.aws/credentials'` in single quotes is a literal relative path.
- Braces are expanded first, as the shell expands them before anything else, so `grep -f.{e..e}nv` is `grep -f.env` and `{-f,-x}.env` is two options. A glob or a brace in a file name is expanded against the folder as the shell would, a leading dot matched only by a literal one, and every file it names is judged: `cat .[e]nv` and `cat *.p12` are stopped when those files are there. One that matches nothing reaches the program as written. A glob that would list more than 10,000 entries, or a brace that makes more than 1,024 words, is stopped.
- A word whose value only the shell knows (another variable, a command substitution) where a program such as `cat`, `head`, `grep` or `source` takes the file it reads is stopped; the same word where it is not a file name (`echo "$PATH"`, a commit message) is fine. A shell that reads its commands from its input (`bash <<EOF`, `curl ... | bash`) is stopped. A file given to a shell or an interpreter to run (`bash -v .env`, `sh .env`, `python3 .env`) is judged as a read, after the program's options, and one only the shell knows (`python3 "$FILE"`) is stopped; a programme string (`bash -c`, whose commands are read as a line of their own, `python3 -c`, `node -e`) is not a file.
- The usual wrappers are looked past: `command` (its options, `-p`, `-v` and `-V`, only before the program; with any other option it runs nothing, which is outside the grammar), `builtin`, `env` (`-C` runs the program in that folder, `-S` is split into words, an option it does not know is stopped), `nohup`, a `time` program, `sudo` (with `-D`), `xargs`, and `NAME=value` in front of a command. `env`, `sudo`, `nohup`, `xargs` and a `time` program start a process of their own, so a `cd` under one of them does not move the shell; `command cd` and `builtin cd` do. `xargs -a` and `--arg-file` have their file judged.
- `cd` (a bare `cd` is your home folder), `pushd` and `popd` move where later relative paths point (`pushd -n` and `popd -n` change only the stack, and an option `cd` does not have, or more than one folder, which bash refuses and zsh reads as a substitution, leaves the folder unknown), from every folder the line might be in. A `cd` after `&&` or `||` that may not run (one after `||`, or after `&&` once the chain stops being only `&&`) leaves both folders possible, and later reads are judged against both. `cd -P`, `env -C` and `sudo -D` resolve links on disk, as `chdir` does, so `env -C link/.. cat credentials` is judged in the folder the link points into; a plain `cd` works on the path as written, as the shell does. `cd -`, `cd "$DIR"`, `cd <(...)`, `popd` past the start of the line and `pushd +1` leave the folder unknown. The `time` keyword exists only at the start of a command: after a wrapper (`command time`) or an assignment it is the time program, a process of its own. After that, a relative read is stopped only if the path could name a key file from some folder: its name is a key file's (`.env*`, `*.pem`, `id_*` and the rest) or one kept in a protected folder (`credentials`, `config`, `known_hosts`, `hosts.yml`), or it passes through a protected folder (`.aws`, `.ssh`, `.gnupg`, `.config/gh`, `.config/mehen`, `.local-secrets`). So `cd "$(git rev-parse --show-toplevel)" && cat README.md` passes, and `... && cat .env` is stopped. This leaves one gap, accepted so that ordinary work in a folder the guard cannot follow is not stopped: a link with an ordinary name in that folder is not checked, so `cd "$DIR"; cat settings`, where `settings` in that folder links to a `.env`, reaches it.
- A path that exists is judged where it really is: its links and `..` are resolved in order, so `link/../credentials` is judged in the folder the link points into. `ln -s` is judged by its target relative to the link's folder (`-t` forms too), `ln` without `-s` by its target relative to the working folder, and a later read on the same line of a link it made is judged by what the link points at. Making a link to a key file is stopped.
- `grep -r` walks the folders it would search, up to 16 folders deep and 10,000 entries, and is stopped if it would reach a key file. `-r` skips the links it meets, as grep does; `-R` follows them, stopping only where a folder would be inside itself. `-d recurse` and `--directories=recurse` count as `-r`. `--include` and `--exclude` work as in GNU grep: "If contradictory --include and --exclude options are given, the last matching one wins. If no --include or --exclude options match, a file is included unless the first such option is --include." `--exclude-dir` leaves a folder out. A search wider than the bound is stopped with a reason that says to narrow it.
- A program that reads files, fed by `xargs` or run by `find -exec` or `-execdir`, reads what `find` selects. The guard follows one form: `find [-H|-P] <start>... <tests>... [-print|-print0] | xargs [-0] <program> [args]`, or the same `find` with `-exec` or `-execdir <program> [args] {} +` or `\;` as its one, last action. The tests are `-name`, `-iname`, `-path`, `-ipath`, `-type f`, `d` or `l`, `-maxdepth` and `-mindepth`, joined by `-a`. It walks each start as `find` would, within the same bounds and skipping the same folders as `grep -r`, so the two behave alike, and judges every entry the tests select as the program would open it: from the program's own folder for `xargs` (an `env -C` or `cd` before `find` moves only `find`), from `find`'s folder for `-exec`, from the folder that holds the entry as `find` reaches it for `-execdir` (for a start that is a link, the link's own folder), links followed. A name with a blank, a quote or a backslash, which plain `xargs` would split, is stopped unless `-print0` and `xargs -0` come together, and either without the other is stopped. Anything else feeding a program that reads files is stopped: `-L`, `-follow`, `-o`, `!`, `-not`, parentheses, `-regex`, `-prune`, `-printf`, `-ls`, `-fprint`, `-delete` or any other test or action, more than one action, an action before a test, `xargs -I`, `-J`, `-a`, `-E` or `-d`, a start, pattern or other test value only the shell knows, a POSIX class in a pattern, a walk past the bounds, or an input that is not such a `find` (`git ls-files | xargs cat`). A `find` that feeds nothing that reads (`find . -name '*.tmp' -delete`, `| xargs rm`) is not checked.
- The walks for `grep -r` and `find` do not go into folders named `.git`, `node_modules`, `.venv`, `venv` or `__pycache__`, which make up most of a typical tree. Neither is checked inside them, but grep and the program `find` feeds still read them, so a key file kept in one of them can reach the agent. Only folders are skipped, and a folder you name on the command line is walked whatever it is called.

**Printing the environment or a key variable:** `env`, `printenv`, `set`, `export`, `declare`, `typeset`, `local` or `readonly` with no names; `printenv`, `echo` or `printf` of a key variable; `declare -p` and its kin with a key variable or a name only the shell knows; and `ps e`, which prints other processes' environments.

**Putting a key into a command or a file:** a command, or a write or edit, that carries a PEM private key, a URL with a password in it, or a token that starts like a provider key (`sk-`, `ghp_` and the others Mehen knows) followed by a random-looking tail. Mehen's own placeholders are not keys and pass.

A blocked agent reads a reason that says what to use instead: `mehen ls` to list keys, `mehen fetch` or `vault_fetch` to make the call, `mehen run` to give a program its variables, `mehen request` to ask you for a key it does not have. You see a short card saying what was blocked.

## Choose what it does

```sh
mehen guard
mehen guard warn
mehen guard block
mehen guard off
```

`block`, the default, stops the call. `warn` lets it through and shows you the card. `off` says nothing. The level is kept in `guard.json` in the Mehen home; `MEHEN_GUARD=warn` (or `block`, `off`) overrides it for one process. `mehen guard` with no argument prints the level in force.

## Keep the agent's shell out of the vault, too

With a vault on the same machine, a program running as you can read the vault's files, and so can an agent's shell. The guard stops an agent's tools reading the data folder, but it reads command lines, which a determined program can disguise. Claude Code's sandbox closes that gap at the operating system's level: turn it on (`/sandbox` in Claude Code), then run `mehen guard install` again. With the sandbox on, the install also adds the vault's data folder to the sandbox's `denyRead` and `denyWrite` lists, so the agent's shell can neither read nor change the vault's files. Claude Code runs its MCP servers and hooks outside the sandbox, so `mehen mcp` and `mehen hook` still reach the vault. The install only touches a sandbox you have turned on, and `mehen guard remove` takes those paths out again. [The threat model](../security/threat-model.md#a-vault-on-your-own-machine) has the rest.

## What each agent enforces

The rules are the same everywhere; what reaches them depends on the hooks each agent offers.

| | Claude Code | pi | Cursor | Codex |
| --- | --- | --- | --- | --- |
| Shell commands | Bash | bash | every command (`beforeShellExecution`) | Bash and `exec_command` |
| The agent's file reads | Read, and Grep and Glob with a path | read, grep, find, ls | every agent read (`beforeReadFile`) | through the shell; Codex's only other file reader is `view_image`, for images |
| Keys written to files | Write, Edit, MultiEdit, NotebookEdit | write, edit | Write (`preToolUse`) | `apply_patch`, the lines it adds |
| When the check cannot answer | goes through, except input `mehen` cannot read (exit 2) | blocked | blocked (`failClosed`) | blocked when `mehen` answers with an error (exit 2); goes through when `mehen` cannot start at all or times out |
| Warn | a card | a notice | allowed; Cursor documents `user_message` for denials, so the card may not show | a `systemMessage` warning |

What is not checked:

- **Cursor.** Its Grep tool and its other tools, and MCP calls: the docs do not describe the input of Read, Grep or Write in `preToolUse`, so the Write check looks for a key in every string of the tool's input and names no file. A denied read shows you the card; Cursor's `beforeReadFile` answer has no field for a message to the agent, so the agent learns what to use instead from the session note. Mehen's hooks are user hooks, in `~/.cursor/hooks.json`, and user hooks do not run in Cursor's cloud agents: those run a project's own `.cursor/hooks.json` and, on Enterprise plans, team and enterprise-managed hooks.
- **Codex.** Input typed into a command that is already running: Codex sends it with `write_stdin`, which does not run `PreToolUse` again, so `cat .env` typed into an interactive shell the agent started is not seen. MCP tools and Codex's other local function tools: Codex runs hooks for them, but Mehen's matcher (`Bash|apply_patch`) leaves them out. Only hosted tools, such as web search, do not go through Codex's local hooks at all. Codex's own docs call tool hooks "a useful guardrail, not a complete enforcement boundary". A hook you have not trusted in `/hooks` does not run at all, and an enterprise `allow_managed_hooks_only = true` skips it too. If the `config.toml` beside `hooks.json` also declares `[hooks]`, Codex loads both and warns at startup; the install says so.

Cursor also loads Claude Code's hooks from `~/.claude/settings.json` while its "Include Third-Party Plugins, Skills, and Other Configs" setting is on, which it is by default. Mehen's Claude Code hooks then run in Cursor beside its Cursor hooks; a denial from either blocks the call.

With Cursor's hooks failing closed, uninstall in order: run `mehen guard remove` before you delete the `mehen` binary, or Cursor blocks every shell command, read and write until you take Mehen's entries out of `~/.cursor/hooks.json` by hand.

## Another harness

`mehen hook check` takes one JSON object on stdin, `{ "tool": "read" | "write" | "shell", "path", "content", "command", "cwd" }`, and prints `{ decision, reason, card, findings }`, where `decision` is `deny`, `warn` or `allow`. A harness with a pre-tool hook of its own can call it and block on `deny`. `mehen hook claude-code`, `mehen hook cursor` and `mehen hook codex` are the same check in each of those agents' hook shapes.
