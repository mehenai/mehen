# Changelog

Changes to the hosted vault first, newest at the top, then the release notes of the `mehen` command line.

## The platform

### Unreleased

`mehen adopt submit` no longer needs a snapshot first for a single `.env` planned with `mehen adopt file`; `mehen adopt retire` still holds the file until a snapshot holds it ([Back up a machine before adopting](guides/backup.md#when-submit-and-retire-need-the-snapshot)). The guard's advice on a blocked `.env` read now names `mehen adopt file <path>`.

From the next release on, each release publishes `ghcr.io/mehenai/mehen` for linux/amd64 and linux/arm64, tagged with its version and `latest`, with provenance and an SBOM attached, and `compose.yaml` pulls it instead of building from the checkout. See [Run it on another machine](start/another-machine.md#or-run-it-in-docker).

`mehen run` now warns, once each and without stopping the run, when a `.env` or `.env.*` file next to the run could hand the program its old plaintext value (with `mehen adopt file <path>` as the next step), when the command starts a Node older than 22.21.0 or 24.5.0, which ignores `NODE_USE_ENV_PROXY`, and when a run with placeholders ends with no connection to their hosts through the local relay. The run CA bundle is also set as `AWS_CA_BUNDLE` and `DENO_CERT`. A new guide, [Which programs work with mehen run](guides/run-compatibility.md), lists the clients checked with placeholders, the ones that do not work, and lease delivery for those.

From the next release, each release is also published on [GitHub Releases](https://github.com/mehenai/mehen/releases), with the same files as `https://mehen.dev/dl/`, its signed manifest and a `SHA256SUMS`. The next `mehen` also accepts a release that lists builds for musl-based Linux such as Alpine, so a later release can add them without stopping older machines' updates; until then, the installer on a musl system says the release has no build for it. A Homebrew tap, `mehenai/homebrew-tap`, exists but has no formula yet. See the CLI's release notes below.

### 20 November 2026: an approved request is sent again without rebuilding it

The next `mehen` release saves a request the vault holds for approval on the machine that sent it, for an hour, and sends it again once a person approves: `mehen fetch --resume <apr_id>`, `mehen wait <apr_id> --execute`, or through MCP `vault_fetch` with `approval` alone and `vault_wait` with `execute`. Each approval is replayed once, through the same checks as a fresh request; a push is never replayed. The vault is unchanged. See [Approvals](guides/approvals.md) and the CLI's release notes below.

### 20 November 2026: custom credentials in the web UI, `mehen.local.toml`, `mehen adopt file`, Docker self-hosting and `mehen` 0.4.2

**Add a credential** in the web app now includes **Other API (custom host)** (with destination host and optional header name), **Database URL** and **Other secret** (lease-only for `mehen run`), so humans can add non-template keys and program secrets directly in the browser under the same binding, injection and passkey checks. The repository now ships a hardened `Dockerfile` and `compose.yaml` (with an optional Caddy TLS profile) for self-hosting `mehen serve`. In `mehen` 0.4.2, a fresh `mehen up` starts guard hooks in `warn` mode (`--guard block` blocks immediately), `mehen init --local` writes an uncommitted `mehen.local.toml` for solo adoption in shared repos, and `mehen adopt file <path>` scans and plans one `.env` file in a single step.

### 20 November 2026: agents see six Mehen tools by default

The next `mehen` release serves six MCP tools by default (`vault_status`, `vault_list`, `vault_request`, `vault_fetch`, `vault_env` and `vault_wait`), a quarter of the tool list a host puts in front of the model in every conversation, and the skill becomes a short sheet that sends an agent to `mehen guide <topic>` for the rest. Every other tool is in an opt-in toolset; `mehen setup --toolsets all`, which writes `MEHEN_MCP_TOOLSETS=all` into each agent's `mehen` entry, restores the full list after a restart. See [MCP tools](reference/mcp.md) and the CLI's release notes below.

### 20 November 2026: eighteen more services have templates, and each template names the variable its SDK reads

New templates: Hugging Face, Replicate, DeepSeek, xAI, Supabase, DigitalOcean, Railway, Render, Upstash, PlanetScale, GitLab, PagerDuty, Jira, Twilio, SendGrid, Discord, Figma and PyPI. Each allows reads only on routes it names, because these APIs have reads that hand back tokens, keys or signing secrets; every other read and every write asks unless the template allows a narrow everyday call by name, such as a model call. Some requests always ask, whatever a credential's own policy says, as does any such request whose body cannot be read: an xAI model call that names a remote MCP server, xAI media published at a public link or uploaded to a URL the request names, a Replicate prediction that names a webhook, a Jira write that may change who can see an issue, and a Jira notification. Where a service documents the environment variable its SDK or CLI reads the key from, the template now names it as `defaultEnvVar`, and `mehen templates --json` shows it. See [Providers and templates](reference/providers.md).

### 20 November 2026: a mandate reads action paths on services nobody has reviewed, and a lost standing stays lost

On a service nobody has reviewed, a `GET` or `HEAD` whose last path segment is an action word is now that act, not a read. `GET /v1/deleteMessage` is a delete, `/v1/editMessageText`, `/v1/logOut` and `/v1/upgradeGift` changes, `/v1/forwardMessage` a change and a send and `/v1/answerInlineQuery` a send, so a mandate with only reads ticked no longer lets them through. Whether such a `GET` only reads is still decided by the words in its address, on a best-effort basis. Telegram's Bot API and Slack's Web API are decided by a method allowlist instead: there a `GET` or `HEAD` reads only for a method shaped as a read (Telegram's `get` methods, a Slack method whose part after the last dot starts with a word such as `list`, `info` or `history`, or the `search` family), any other method is a change on every HTTP method, and one that delivers or alters what a chat sees, such as `sendMessage`, `answerCallbackQuery`, `editMessageText`, `pinChatMessage`, `chat.meMessage`, `chat.update`, `reactions.add`, `reminders.add` or `bookmarks.add`, is a send too, on every HTTP method, on `slack.com` and a workspace's own subdomain alike. The floor still makes Telegram's `getChatMember`, `getChatMemberCount` and `getWebhookInfo` ask. A word counts in any letter case, since a service such as Telegram reads a method name in any, and the capitals a sender chooses can only add a match, never take one away. A delete word, one of the floor's or `prune` or `clear`, counts anywhere in a run of letters (`DELETEmessage`, `deletesTory`, `bulkdeletemessages`), except at its start when all that follows is an inflection, alone or then a word such as `list` or `page` (`archived`), and an act word at the start of a run when more than that follows it (`postsTORY`) or after `bulk`, `batch`, `mass`, `multi` or `un` (`bulkupdate`, `unpin`), so `getUpdates`, `/settings`, `/settingsPage`, `/posts` and `/postsList` stay reads, while `getDeletedMessages` and `postsByUser` ask, and a last segment with a digit in it is an ID, never an action. A query parameter that names the method, `method`, `action`, `op`, `cmd`, `do` or `operation` in any letter case, names its act or delete in any part of its value, split at everything but a letter or a digit, not only in the last: `GET /services/rest?method=flickr.photos.delete` and `GET /api?action=delete_item`, `delete-item` or `deleteItem` are deletes, and `?action=edit_profile` a change. Its value is also read, part by part and camelCase word by word, for the words the floor reads in a path, on a `GET` only its verbs such as `send`, `publish` and `refund`, so `GET /http-api.php?action=sendsms` is a send; and one that acts and names access, such as `?action=set_acl`, `add_member` or `grant_access`, is sharing, which no mandate covers. A write whose last path segment is a delete word, or whose segment before up to two IDs at the end, or before a last `all`, `bulk` or `many`, is, such as `POST /v1/tasks/7/delete`, `POST /v1/delete/7/8` or `POST /v1/delete/all`, is a delete as well as a change. A signer who stops managing a credential's home now lapses the mandate until they resume it, as other changes to their standing already did, even if the management comes back. That covers a share lowered from manage, removed or past its end date, leaving or deleting a team that manages a project, and moving a credential out of a home they manage. A share past its end date counts before the sweep reaches it: the next request a mandate would cover, on any credential it names, lapses the mandate first and asks, and planning or resuming a mandate does the same, so the resume asks for the passkey; any change to teams, shares, roles, a credential's home or a credential made or deleted first lapses what it took, judged on access as it was, and each end is judged once, by the share and its terms, never against a clock watermark. Once judged, the share counts as ended until its terms change, even if the clock is set back. It lapses only a mandate that lists a credential homed there, or all of them, and never one whose signer still manages the project, as an owner or admin always does. The lapse leaves the mandate's revision alone, and the audit records it as `mandate.lapse` with its cause. A mandate is standing authority: the signing session's identity check reaching its expiry does not lapse it, while the identity provider invalidating that check, a rule change or a new gate generation does. Revoking a machine, or removing its owner, now ends its mandate for good: it is stopped, its proposals close, and it cannot be resumed or signed again. A machine enrolled again can have a new one. See [Mandates](concepts/mandates.md#what-never-means-on-a-service-nobody-has-reviewed).

### 20 November 2026: a relayed write the upstream did not answer no longer says retry later, and a relay refusal says whether anything was sent

Every `/v1/relay` refusal now carries `Mehen-Forwarded`: `no` when the vault refused before it sent anything upstream, `yes` when it refused after (`upstream_failed`, or `too_large` for the upstream's answer to a write, which now says the request was sent and to check first). `mehen` sends a write again only after a refusal marked `no`. See [HTTP](reference/http.md#headers). When the vault could not get an answer from the upstream for a relayed request with a method other than `GET`, `HEAD` or `OPTIONS`, `upstream_failed` now says the request may have reached the service and to check whether it took effect before sending it again, and carries no `retryAfter`. A read still says to retry later, with `retryAfter: 5`. See [`upstream_failed`](reference/errors.md#upstream_failed).

### 20 November 2026: an approval shows the agent's session

The page for a request held for a person, and its row in Needs you, now show the session label the agent signed the request with (`MEHEN_SESSION`), marked as the agent's own words, as an intake's page already did. Before, an approval always said "Session: not given".

### 19 November 2026: connections survive network errors, keep their scopes and say when one dies

A workspace OAuth connection whose renewal fails on a network error, a timeout, throttling or the provider's own failure now keeps using its current token while it lasts and retries, backing off from 30 seconds to an hour and waiting out a provider's `Retry-After` (up to 24 hours). It needs a reconnect only when the provider says the grant is gone, such as Google's `invalid_grant`, GitHub's `bad_refresh_token` or Microsoft's sign-in-again errors, and the reason is named: the person who connected it left, its OAuth client was replaced, a Testing-mode app's 7 days ran out, or an interrupted refresh had already used the token. A renewal that keeps failing for four days is flagged for review and the people who may reconnect it are told once, while the vault keeps trying. Those people also get one notice when a connection stops, and Needs you shows one **Reconnect** row with the reason, which opens the agent's reconnect link when there is one. An OAuth client its provider rejects pauses every connection that uses it and shows one **Replace the client secret** row instead; replacing or restoring the secret clears it. A reconnect keeps every scope the connection held. A person's signed settings change is no longer refused because the vault renewed the token meanwhile. A rule or task grant that ends with its credential says it was replaced, reconnected or edited. A credential's page lists only the policy floors on paths its binding admits. Asking for a Google service account key or a GitHub App is refused, since nothing could use one yet. See [When a refresh fails](guides/oauth.md#when-a-refresh-fails).

### 19 November 2026: a first run on a local vault reads right

The pages a person sees during `mehen up` say what is true on a vault on their own machine. The enrolment page says "You are: on this machine" when the browser is on the vault's machine, and an accepted machine's page says the terminal that asked carries on by itself, unless an agent asked. A vault with no account yet welcomes its owner by name in the tab, does not look the sign-up code up as an invitation, and offers no sign-in. The recovery codes have Copy and Download (`mehen-recovery-codes.txt`) beside them, and a second passkey is offered below them; one code is still typed back. A new workspace's short name follows its name as it is typed until it is edited. A workspace's home checks Needs you every 20 seconds while it is open, so a machine waiting just after the workspace is made appears without a reload, and its Get started card stops offering to connect a machine once one of yours is enrolled. The search box shows Ctrl K off a Mac, and the fingerprint field on the enrolment page scrolls clear of the Accept bar.

### 19 November 2026: the installer checks the release's signature

`https://mehen.dev/install` checks the release manifest's ES256 signature against Mehen's release keys before it trusts any checksum in it, so a changed manifest or binary on the way is refused with nothing installed. It needs `openssl`. See [Keys, proofs and signing](security/keys-and-signing.md#releases).

### 19 November 2026: one passkey from sign-in to approve, one code for Review together, and owners told about unshared projects

Signing in with a passkey in the browser now opens the 15-minute window for that session, as a passkey confirmation already did: open the agent's link, sign in and press **Approve**, and the passkey is asked for once. The window's rules are unchanged, and what always asks for a fresh passkey, such as signing a mandate or setting how often Mehen asks to Let it work, still does. A machine at its 20 open asks is refused with a link to where the person decides them: the Review together page of its oldest open ask when that ask is grouped, else the ask's own page, else the workspace's home; the cap does not move. Each review group and bundle has one code, which `mehen` prints with the group's link and the page asks the person to tick, in place of checking every ask's code; an ask that joins the group while the page is open clears the tick, and a passkey only signs the asks the page showed. When a member's machine is refused a run because the project is not shared with that member, the refusal links to the project's page and the people who may share it with that member (for a guest, only owners and admins) get a share request in Needs you, once a day, whose **Share** button opens the Shared with form with the member chosen. See [Approvals](concepts/approvals.md#deciding-several-together).

### 19 November 2026: a machine proposes a mandate only for what it asked for

A machine's mandate proposal may now name only the credentials, and the kinds of request besides read, that the machine itself asked for in the last 30 days: its own held requests that carried a `mandateCover` hint, and the requests its own mandate let through. Another machine's asks never count, nor an ask a person rejected, nor a credential the machine can no longer reach, nor anything dated after now. A refusal's `next.command` keeps the proposal's hours, and a proposal keeps the credential behind each slug it names: deleting one closes the open proposals naming it. On upgrade, every unsigned open proposal from before closes, binding none, with a note that the machine can propose again. Renewing or copying a mandate opens the sign page narrow, with the old terms in words behind **Use these terms**, and fresh forms and newly ticked kinds start at 500 reads, 100 changes, 10 sends and 5 deletes a day. The sign page opens a proposal on its own terms only and, without one, on read alone, no credential and 30 days, whatever its address asks; `?items=all` and `?classes=` no longer preselect anything. It may also last at most 30 days and ask for at most 500 reads, 100 changes, 10 sends and 5 deletes a day. A proposal that names every credential, anything else, a longer term or a higher cap is refused with `forbidden` and `mandateRefused` (`items_all`, `item_unasked`, `class_unasked`, `term_too_long` or `caps_too_high`); the message says what to drop or lower and `next.command`, when present, proposes the same terms cut to what is allowed; it is left out when there is no valid bounded retry: nothing asked for, more than 200 credentials, or an explicit list sharing none with what was asked for. A vault upgraded to this starts from the held asks with a hint it still keeps, about the last two days, and from each machine's own mandate uses of the last 30 days. `GET /v1/mandates/asked` tells the machine what that is, and `mehen mandate propose` proposes exactly that by default, for 30 days at low caps. The person who signs may still widen any term, length and caps included, on the sign page, with the passkey as before. See [Mandates](concepts/mandates.md#how-a-machine-asks-for-one).

### 19 November 2026: choose how often Mehen asks

A workspace's Settings page has a new choice, **How often Mehen asks**: Ask on writes (as before, the default) or Let it work. At Let it work, a request within a credential's destinations that the workspace owner's trust would cover goes through without asking, and anything that would still need a person is refused at once with the reason, so an agent never waits. It never covers protected environments, browser fill, pushes into other services, the policy floor or machines the owner's trust does not reach, and it follows Mehen's reviewed templates as they are updated. An owner or admin chooses Let it work with a passkey; going back needs none, and every change is in the activity. It is on in a local vault and off on Mehen Cloud for now. See [How often Mehen asks](concepts/approvals.md#how-often-mehen-asks).

### 8 November 2026: a held request says when a mandate would let it through

When the vault holds a request from a member's machine, and a mandate its owner could sign would cover that kind of request, `approval_required` now carries `mandateCover`: the kinds a mandate would need, a state (`none`, `unticked`, `paused`, `tripped`, `ended`, `outside_schedule` or `not_covering`), and the machine's mandate and its page when it has one. Each held request of a bundle carries it too. A guest's or a team's machine never gets one, nor a workload. The ask page offers the machine's owner "Let build-box carry on with requests like this", which opens the sign page with those kinds ticked, or a link to the mandate when it is paused or tripped. A request held only because a cap was reached carries `mandate` with the caps reached instead. In the same change, proposing the same terms and reason while they wait hands back the same link with `existing: true`, signing a mandate closes the machine's other open proposals, a mandate names the proposal it was signed from, a workload may pause its machine's mandate, and a lapse is never silent: its signer is told once, and the home asks them to resume it. See [The cover hint](concepts/mandates.md#the-cover-hint).

### 8 November 2026: the floor reads a JSON body as GraphQL only when it is GraphQL, and knows Analytics Engine SQL

Before a standing rule, task grant, posture or mandate stands in for a person, a GraphQL body needs a proof the vault can read field by field. Any JSON object with an `id` or a `variables` counted as GraphQL, so an ordinary REST create that names its own `id`, such as creating a Cloudflare AI Gateway, always asked. Now a JSON body is GraphQL when it has `query`, `operationName`, `extensions`, `documentId` or `doc_id`, a `variables` that is not a list, or an `id` together with `variables`; on a path with a segment naming `graphql` or `gql`, an `id` or a `variables` alone is enough. Cloudflare's reviewed list is at version 2, which adds Workers Analytics Engine SQL (`POST` to an account's `analytics_engine/sql`, one statement sent as plain text or as a form) as routine building in the `workers` area; a mandate reads it as a change. A Cloudflare posture or task grant approved before covers it only once approved again. See [Policy](concepts/policy.md#the-shape).

### 8 November 2026: one passkey, then 15 minutes without asking again

After a real passkey confirmation in the browser, further confirmations in the same browser session no longer ask for the passkey for 15 minutes, for actions that cannot widen access: deciding approvals, one at a time or up to 25 together, denying a rule proposal, storing a credential from an intake, starting a connection, creating a project, narrowing or revoking a machine and the others [The 15-minute window](concepts/approvals.md#the-15-minute-window) lists. The window does not slide. It ends early when that session signs out or is ended, when the account's security changes, when the passkey that confirmed is removed, and when the account starts cooling off or has a security change pending. Whatever can widen who can act or what a credential is exposed to still asks for a fresh passkey every time: passkeys and recovery codes, members and invitations, a credential's binding, policy or ceiling, sharing a project, approving a standing rule or task grant, setting how careful a credential is to anything but asking, and signing a mandate. The account page says until when a confirmation holds, and **Ask every time** ends the window at once. A confirmation inside the window is marked as one in the audit, with when the passkey was used.

### 8 November 2026: mandates: a machine carries on without asking, on terms its owner signed

A person can now sign a [mandate](concepts/mandates.md) for one of their own machines, with a passkey: which credentials, which kinds of request (read, change, send and delete), how many of each a UTC day, an end at most 90 days away and, if they choose, only certain hours. While it is active, the vault lets the machine's held requests of those kinds through on its own key, keeps a receipt of each under **Went through on trust** for 30 days and counts it against the day's caps. It is the only standing approval that covers sends and deletes, and services nobody has reviewed. Minting or reading credentials, money, sharing, members, webhooks, a request Mehen cannot read, a live key, a protected credential, a workload's request and anything in a managed or frozen workspace still ask every time. More than 120 requests beyond reading in a minute trips it, and a change to the signer's standing (a role change, a suspension or removal, an account recovery, signing out everywhere) lapses it until they resume it with a fresh passkey; revoking the machine ends its cover for good, and a credential whose home the signer no longer manages is no longer covered. A machine asks for one with `mehen mandate propose` and hands over the sign page; it may pause its mandate, but never signs, resumes or stops one. The vault switches mandates on workspace by workspace; where they are off, every mandate route answers as an unknown route does. See [Agents that work on their own](guides/unattended-agents.md).

### 6 November 2026: put a credential into another service's secret store

A machine can ask for one secret field to be put into a GitHub Actions, Vercel or Cloudflare Workers secret store (`POST /v1/push`). A person approves every push on its own page, after reading the exact destination; the vault then reads the value and calls the provider itself, so the value never reaches the machine. A credential is pushed only once someone who may change it allows that on its page, and no standing rule, task grant, posture or mandate ever covers a push. The credential's page lists where it was pushed; a guest's list names no one who pushed. A push is never decided through an app's own passkey prompt; it is decided on its vault page. Switched on workspace by workspace, and never in a managed workspace. See [Put a credential into another service](guides/push.md).

### 6 November 2026: type a credential into a web page

A machine can have one field of a credential, a password, username, one-time code or API key, typed into one checked field of its own browser (`POST /v1/fill`). The vault seals the value to a key made for that fill alone. On a credential's page, the In web pages card says whether it may be typed into pages and which ones, at most 8 https origins in each list, and the machine's scope must allow it, which the vault adds only once the machine has run `mehen` 0.3.17 or later. A sign-in's username is typed without asking; its other fields ask first, one approval covering up to 6 fields on that page within 10 minutes; another service's page asks every time. Switched on workspace by workspace, and never in a managed workspace. See [Type a credential into a web page](guides/fill.md).

### 6 November 2026: task grants, and how careful a credential is

A person can let an agent carry on with routine building in named areas of a reviewed service for 15 minutes, an hour or four hours, up to 200 requests: a [task grant](concepts/policy.md#task-grants), started from **Approve, and let this agent carry on** on a held routine request, or proposed by the agent from a held request with `--area`. Each credential on GitHub, Stripe or Cloudflare also has a [posture](concepts/policy.md#how-careful-a-credential-is), set in its **How careful** card with a passkey: ask for every change (the default), let routine building through, or trust the machines of the people who manage its home. A posture never covers a delete or a route the reviewed list marks destructive, such as moving a Worker's live traffic, nor secrets, sending, sharing, payments or anything the vault cannot read. Cloudflare's reviewed list now names its routine, destructive and floor routes for Workers, routes, KV, R2, D1, queues, Pages, AI Gateway, Vectorize, Workflows and DNS. **My rules** and the credential's page list each grant with its uses and end. Both are switched on with standing rules, and never in a managed workspace.

### 6 November 2026: decide a task's asks together, and ask for several writes at once

Open asks from one machine, one task and one credential now show as one row in Needs you with **Review together**. An agent can also ask for up to 20 writes at once (`POST /v1/approvals/bundles`, which `mehen plan submit` calls): the vault checks each without sending any and holds those that need a person in one bundle, `bnd_...`, at one link. On the Review together page, `/w/<slug>/g/<id>`, requests no floor holds are ticked at first, those that send, pay, share or change a credential start unticked with why, and a protected run, a four-eyes or warned ask stays on its own page. One passkey decides up to 25, signing each entry exactly as its own page would, and the vault decides each in its own transaction and reports each one. A batch never makes a standing rule or task grant. A machine can also replace its own open ask with a corrected one (`replaces`), which then reads `superseded`. Switched on workspace by workspace; where it is off, bundles and `replaces` are refused with `forbidden`. See [Deciding several together](concepts/approvals.md#deciding-several-together).

### 5 November 2026: a grant is found by the request, and a spent approval says so

A relayed request sent again without its approval id now spends the grant the human gave it, as [Approvals](concepts/approvals.md#grants) has always said. It opened a second approval instead, so a script that waited for the approval and repeated the request asked the human twice for every write. The grant must be this machine's, or this workload's, for exactly the same request, approved, unspent and inside its window. An approval that was spent or stopped now reads `used` or `revoked` after its hour instead of `expired`, and an approval that was given but never used reads `expired` with the time it was approved, so `mehen wait` no longer says it expired before a decision.

### 3 November 2026: connections ask for scopes an agent can work with

A connection that names no scopes now asks for more. GitHub asks for `repo` and `read:user` instead of `read:user` alone, so an agent can reach your repositories, private ones included. Microsoft 365 asks for `User.Read`, `Mail.ReadWrite`, `Mail.Send` and `Calendars.ReadWrite` instead of `User.Read` alone, for mail and calendar. Google Drive asks for `drive`, all your files, instead of `drive.file`, only the files the app made or you opened with it. The policies are as before: reads go through, and every write needs your approval or is refused. Sharing a Microsoft calendar now has its own approval rule, as sharing a file already did. A connection you already have keeps the scopes it was granted. Connecting it again without naming scopes asks for the new defaults, and the connect page marks each scope that is new; `--scopes` still asks for exactly the scopes you name. See [Providers and templates](reference/providers.md#oauth-providers).

### 3 November 2026: the vault recommends the published release

Every answer the vault gives `mehen` names the version it recommends, and a `mehen` below it checks for an update at the end of that command. That version was set by hand and lagged releases. The vault now recommends the published release, usually within five minutes of its publication, on a machine's next calls to the vault, once the release is signed by one of the release keys `mehen` itself trusts; the version set by hand is now the lowest it recommends. A vault server that has just started recommends the version set by hand until its own first read of the release. Pausing a release lowers the recommendation again, usually within five minutes. The minimum version, which forces an update, is still set by hand. See [Keys, proofs and signing](security/keys-and-signing.md#releases).

### 3 November 2026: `mehen wait` hears an approval at once

`mehen wait` on an approval returns as soon as it is decided, instead of up to 25 seconds later. Waits on credential requests and adoptions now rest until something in the workspace changes, instead of checking ten times a second, so they no longer hold up the workspace's other reads.

### 3 November 2026: a machine finds the project its checkout's remote is

A machine can now ask the vault which project a git remote is bound to, with `GET /v1/projects?remote=<remote>`. The vault answers only when the machine may use that project, with its id, slug, default environment, environments and the names of its variables, never a value or an item; a remote bound to a project the machine may not use answers exactly as one bound to nothing. `mehen init` uses it to bind a fresh clone or worktree of a repo that is already a project, instead of trying to create a second one. See [Project variables with mehen run](guides/projects.md#a-repo-that-is-already-a-project).

### 2 November 2026: secrets with no host, so adopt stores a whole .env

A credential with no template, of a kind the relay never puts into a request (such as `generic`, `database-url`, `file`, `hmac-key` or `ssh-key`), that is asked for or adopted with no host and no injection is now lease-only, instead of being refused with "A custom credential needs a binding.": a secret such as `JWT_SECRET`, `SESSION_SECRET`, `REDIS_URL` or `DATABASE_URL` that only `mehen run` delivers, into a process. The vault never sends it anywhere: the relay refuses every destination for it and a run never swaps a placeholder for it. It keeps its kind's ceiling, and its pages say what that allows instead of a host: "No host: only delivered into a process with `mehen run`" at a lease ceiling, otherwise "No host: stored only", with how a human allows `mehen run` where the kind can be leased. A member can give it hosts later by changing its binding with a passkey. `mehen adopt submit` now uploads these rows, and `mehen request` without `--host` asks for one. A kind the relay injects (`api-key`, `bearer-token`, `basic-auth`, `custom-headers`, `oauth-connection`) and a credential proposed with an injection still need hosts, and `mehen adopt plan --check` refuses such a row as the vault would. `mehen wait`, `ls`, `show` and `check` say "no host" too. See [Credentials](concepts/credentials.md#bindings).

### 2 November 2026: Mehen emails the invitation link

Making an invitation bound to one email now offers Email the link to them, ticked by default: Mehen sends the link to that address as it makes the invitation, from `no-reply@mehen.dev`, saying who invited them, to which workspace and as what, that the link works once and only for that address, when it expires, and to ignore it if it was not expected. The link is still shown to copy whatever happens. An open guest link is never emailed. One account sends at most 10 invitation emails an hour and 30 a day, and one address receives at most 3 a day; past either, or if the email cannot be sent, the invitation is still made and the page says the link was not emailed. A sent link is recorded in the workspace's audit log with the address. See [Workspaces](concepts/workspaces.md#invites).

### 2 November 2026: the operators' Settings and Audit views

Mehen's operators now decide in the app whether every account may create workspaces or only the accounts an operator allows, from a new Settings view. Narrowing it is one operator's call with a passkey; widening it again needs a second operator, and never goes past what the deploy allows. An operator's decision for one account still wins. The view also shows the sign-up setting, which stays invitation only: request access and open sign-up are not available yet, and sign-up has not changed. A new Audit view lists every operator change, proposal and platform change, newest first, with filters and the names of who proposed and who approved each one. It says plainly that it is a record in the database, not a tamper-evident chain.

### 2 November 2026: workspaces in the operator console

The Operator area has a Workspaces view: every workspace, searched and filtered, with its owners by name, its people counted and who created it, and one workspace with its backups, its restores and its operator events. One operator can freeze a workspace with a passkey, as a brake: it is the workspace's own freeze, recorded in its audit as that operator, and only its owners unfreeze it. Restoring a workspace, to a point in the last 30 days or from a day's dump, is proposed by one operator and approved by another, each with a passkey, after the page shows the steps to take around it. Its owners and every operator are told of both. See [the threat model](security/threat-model.md#freezing-and-restoring-a-workspace).

### 2 November 2026: an invitation without a Google account

An invitation bound to one email can now be verified with a six-digit code that Mehen emails to that address, beside Verify with Google. The code works for 10 minutes, only in the browser that asked for it, and dies after five wrong tries; an invitation is sent at most three codes an hour and five a day, and takes at most ten wrong tries a day across all its codes, after which the page says to verify with Google or ask for a new invitation. One address is sent at most five codes an hour and ten a day across all its invitations. Where the workspace asks for a Google Workspace account for the invited role, the page offers only Google and says why. If the email cannot be sent, the page says so and Google is still there. A code proves the email just as Google does, so an invitation that lets the person straight in does so either way. See [Connect your agent](start.md).

### 2 November 2026: the Accounts view

Operators now see every account in the Operator area: searched by name, account id or Google sign-in email, filtered to the suspended, those cooling off, those without recovery, those in no workspace or the operators, and each account's workspaces, passkeys, sessions and events, never a key or a token. On an account's page an operator allows or denies its workspace creation, or returns it to the default, and suspends or lifts a suspension, each with a passkey. A suspended account's sessions end and it cannot sign in until lifted; its machines keep their scope, and each of its workspaces' owners and admins is told. Recovering access to an account and deleting one need a second operator to approve, and the operator who proposed a recovery takes its single-use link once. See [the threat model](security/threat-model.md#operators-and-the-two-person-rule).

### 2 November 2026: several operators, and two of them for a change to who is one

Mehen can now have several operators, each one an account with recovery set up, at least two passkeys with one of them a security key, no cooling-off and no security change pending; the Operator area says exactly what an operator's account still lacks before it refuses a change. A new Operators view lists every operator and every change to the role. Making an account an operator, or ending another operator's role, is proposed by one operator and approved by a different one within 24 hours, each with a passkey, and a new operator accepts on their own account page with their own passkey. An operator resigns their own role alone. Every proposal and change is recorded and every operator is told. See [the threat model](security/threat-model.md#operators-and-the-two-person-rule).

### 2 November 2026: invited people join straight away

An invitation bound to an email, for a member, admin or guest, now lets the person in as soon as they prove that email with Google, set up their passkey and recovery, and join: there is no wait for an owner or admin to confirm them, and they land on Connect an agent. The inviter's passkey already signed the invitation's terms, including this choice, and the vault checks again at joining that the inviter may still invite that role. The inviter gets a notice in Needs you when the person joins, and the log shows the inviter's confirmation. To confirm someone yourself, tick "Confirm them myself when they join" on the invite form. Owner invitations and open guest links always wait for confirmation, as do invitations made before today. The People page says which applies to each invitation. See [Workspaces and people](concepts/workspaces.md#invites).

### 2 November 2026: a passkey that syncs is a way back in

A passkey that syncs through a password manager, such as iCloud Keychain or Google Password Manager, now counts as a way back in, so an account with one can join and create workspaces without recovery codes, and signing up skips the recovery step. Your account page then says recovery codes are a second way back in rather than asking for them. Each sign-in and passkey confirmation reads again whether the passkey syncs; if it stops, nobody is signed out, but the next join or new workspace asks for recovery codes or a second passkey first. For a passkey that does not sync, the first recovery codes made within 15 minutes of signing up no longer ask for the passkey again. See [Workspaces and people](concepts/workspaces.md#accounts).

### 2 November 2026: joining lands on Connect an agent

Once an owner or admin confirms a new member, the page that was waiting opens the workspace's Connect an agent page, with the prompt ready to paste, instead of the workspace's home. While a workspace that checks identities with Google still needs that check from this browser, it opens the home as before. Signing in later, or picking a workspace from the list, lands where it always has. When the invitation's email was verified with Google, the sign-up form's "Your name" now starts as the name on that Google account, and can be changed before the passkey is made. See [Connect your agent](start.md).

### 2 November 2026: anyone with an account creates workspaces

Every account can now create its own workspaces from its Workspaces page, with no cap on how many, unless Mehen's operator has turned that off for the account; its New workspace page then says so. Creating one still needs a passkey confirmation and recovery set up first. A workspace also no longer stops at 100 members or 20 open invitations. Rate limits, and the 20 open asks a machine may have, stay as they were. See [Workspaces and people](concepts/workspaces.md#workspaces).

### 1 November 2026: the adopt review page

The review page for a batch from `mehen adopt` leaves an item unticked only when every copy of it is possibly stale, so a backup copy beside the live file no longer drops the live key. Its note says how many copies are possibly stale. See [Bring a machine's credentials into Mehen](guides/adopt.md).

### 1 November 2026: adopting a machine's credentials

A machine can now bring the credentials it already holds, in `.env` files, settings files and its services' env files, into the vault in one batch that a person approves with one passkey. The machine seals each value before it uploads it, and nothing is stored until the approval. The batch's review page lists every row by repository and folder, with where it would send the credential (a destination no template vouches for in red, every host spelled out), the home it would go to, each secret field as its length, its well-known prefix and a fingerprint, and where it was found; no value is ever on the page. Rows with a problem, only stale sources or a custom destination start unticked. Approve stores every ticked row in the home chosen, or nothing if any row fails a rule, and the page marks the rows to fix. A batch is open for 24 hours, and cancelling it, letting it expire or revoking its machine erases what was uploaded. The machine needs `mehen adopt`, which comes with `mehen` 0.3.2; 0.3.1 does not have it. See [Bring a machine's credentials into Mehen](guides/adopt.md) and [Back up a machine before adopting](guides/backup.md).

### 1 November 2026: service runs

A run now has a service form with no maximum life: it lives as long as it renews. Only a machine a person has allowed to run services starts one: tick **May run services** on the machine's page and sign it with a passkey, and since that widens the machine's scope, its owner accepts it with theirs (on a team's machine, an owner's or admin's passkey applies it at once). A protected environment refuses a service run with `environment_refused`. Every renewal plans a service run again, and a variable bound to something else, an override set or cleared, a changed delivery, a rotated credential or a changed fence on another environment ends it with `conflict`, so its supervisor starts it again with the new plan. Unticking May run services applies at once and ends the live service runs of the owner's machines. Every run and renewal also now names the run's hard end, `endsAt`, or `null` for a service run. The machine needs `mehen run --service`, which comes with `mehen` 0.3.2. See [Service runs](concepts/projects.md#service-runs) and [Keep a service running with mehen run](guides/services.md).

### 1 November 2026: backups

The vault is backed up every day. Each workspace not managed by a platform is copied once a day, encrypted under a key derived from the vault's root key, and the daily copies are kept for 35 days and the first of each month for 12 months. Every workspace's stored data also has 30 days of point-in-time recovery. A copy opens only as its own workspace, so it lets no one read what the root key does not already open. If a workspace is ever restored, its audit says so and names the point it went back to. See [Limits, stated plainly](security.md#limits-stated-plainly).

An owner can now take their own encrypted export of a workspace. They add an age key in Settings, under Backups, with a passkey; it works 24 hours later, and every owner and admin is told when a key is added, when it starts working and when it is removed. Any owner can remove one. Only the owner who added a key exports to it, from Settings or with `mehen backup export` on one of their own machines, never a workload or a team's machine. The vault encrypts the export itself, so the browser or machine only ever receives ciphertext, and stock `age -d` opens it. An export holds the workspace's credentials, those of the projects the owner manages and the owner's own private ones; never another member's private credential, a four-eyes credential or an OAuth connection's tokens. Each key takes one export every 10 minutes, and each export is audited and recorded as an [exposure](concepts/credentials.md#the-exposure-ladder) of every value it holds. Whoever holds the key reads every value in an export made to it, for good: rotating or deleting a credential in Mehen does not recall an export, only rotating it at the provider does. A platform-managed workspace has no exports. `mehen backup export`, `status`, `open` and `compare` come with `mehen` 0.3.2. See [Credentials](concepts/credentials.md#homes) and [the threat model](security/threat-model.md).

`https://mehen.dev` answers an agent that asks for markdown (`Accept: text/markdown`) with a short markdown page: what Mehen is, the prompt to give an agent, links to `setup.md` and `llms.txt`, and the install line. ### 31 October 2026: private credentials on by default for your own machine

When an owner, admin or member accepts a machine as their own, the enrol page now ticks "It may use my private credentials", in a shared workspace too: before, it was ticked only for a workspace's only member, so a colleague's first `mehen request`, which asks for a private credential by default, was refused until they turned it on from the machine's page. A guest's own machine still starts with the tick off, a team's machine never has private credentials, and a machine enrolled with `--no-private` still offers no tick. The person can clear the tick before they sign, and their passkey signs what the box says. See [Machines](concepts/machines.md#scope-and-reach).

### 30 October 2026: held requests through a run

A request through a run that a credential's policy holds is now asked for a decision as a request naming the credential is: `approval_required` with the approval and its binding code, decided by the platform in a managed workspace or by a person on the approval page, after which the same request through the run, with the approval id, goes through once; a denial stays final. When the run's workload or machine was limited to placeholders, as a platform's computer is, the vault answered `not_found` instead, which a platform reads as the run's environment gone. The approval names only the credential the run's placeholder stands for, serves only the workload that asked, and only a placeholder in that environment, never a relay naming the credential. The workload that asked now also sees such an approval in `GET /v1/approvals/<id>` and its pending list.

### 30 October 2026: the operator console and platform admins

Mehen's operator can now manage platforms in Mehen's web app as well as from their own machine: an operator console on one account that the operator marks from their own machine, never from the web. It lists every platform with its status, subjects counted by status, keys, limits and admins, and does everything the operator's own commands do, with the same checks: register a platform (with a public key pasted, or a key pair made in the browser whose private key is shown once and never sent), suspend, resume, rotate or revoke a key, set limits, delete every subject, retire, and add or remove the platform's admins. Every change needs the operator's passkey for that exact change, and a destructive one, or one that adds a key, the platform's slug typed back; each is recorded in the platform's events and gives the operator a notice. Every other account finds no such pages.

The operator can also **remove** a platform: it is retired at once, every subject is deleted and purged, and then its slug is free to register again, while its registration, keys, events and its subjects' tombstones stay for the record.

A platform can now have **admins**, Mehen accounts the operator adds, who see their own platforms in a Platforms area: status and limits, subjects counted by status, usage, events, keys and defaults. With a passkey for each change they edit the defaults, add a key with an overlap, revoke a key (never the last), and delete one subject. A key added by the operator or an admin is the platform until it is revoked, so adding one needs the slug typed back and tells the operator and the platform's other admins. See [Platform admins](concepts/platforms.md#platform-admins), [Your platform in Mehen's web app](guides/build-on-mehen.md#your-platform-in-mehens-web-app) and [the threat model](security/threat-model.md#an-operators-session-in-the-web-app).

### Platforms

A business can now build on Mehen as a platform and serve its own users through Mehen's API, without those users ever seeing Mehen. Mehen's operator registers a platform with the public half of its key. The platform creates one managed workspace for each of its users, provisions a device for each agent it runs, adds keys its users type into its own pages (sealed in their browser, so its servers never see them), connects accounts with each user's own OAuth app and the platform's own callback, decides the requests Mehen holds, keeps environments for its tasks, and deletes a user's workspace when they leave. Its defaults and limits apply to every one of its workspaces, read live, and every audit row in them names it. In a managed workspace a credential's policy is the catalogue's current one plus the platform's stricter rules, computed at each use, so a catalogue release reaches those credentials when it ships. Nothing changes in people's own workspaces. See [Platforms and managed workspaces](concepts/platforms.md), [Build on Mehen](guides/build-on-mehen.md) and [Platform API](reference/platform.md).

An OAuth app may now carry its own provider definition instead of naming one of the catalogue's providers, so a connection can reach any OAuth 2 service: its authorisation and token URLs (https, on a public host), its scopes, PKCE, how the app authenticates with its client secret, and the API hosts the token may go to. Public apps, with no secret, are not supported yet. The definition is fixed once the app is stored, the client secret goes only to its token URL, and every request with such a connection is held for a decision unless reads were let through. In this release a platform adds one through the platform API; Mehen's own pages do not offer it yet. The catalogue's Google, GitHub and Microsoft app templates now carry step-by-step set-up, which a platform's page shows beside the form.

`@mehen/client` gains a platform client and `@mehen/client/seal`, a browser entry for sealing. Two error codes are new, both only ever a platform's: `platform_suspended` and `quota_exceeded`.

A platform's `projects.create` with a name the user's workspace already has, and the same environments and default environment, now answers that project with 200 instead of `conflict`, as `devices.create` does for the same key, so a platform that lost the answer can ask again; the same name with other environments or another default environment is still a `conflict`.

### 29 October 2026: runs for workloads pinned to a project

A workload whose scope names a project in `projects` may start a run there with no remote (`remote: null`), even when the project binds remotes: its machine chose the project for it, and it has no checkout to mismatch. Renewing and relaying through such a run no longer checks that a remote is still bound; every other check stays. A machine's own key, a workload scoped otherwise, any run that names a remote, and every protected environment are checked as before. This lets a hosted platform give a task a project environment's variables ([A project's environment for a hosted task](guides/harnesses.md#a-projects-environment-for-a-hosted-task)). `@mehen/client` gains `runs`, `project` and `relayStream`, and relays through a run.

`@mehen/client`'s `relayStream` no longer keeps the request body for the life of the answer stream: it is free to be collected once the vault's headers arrive, and `relay` no longer holds it while the answer is read.

### 29 October 2026: workloads, a key per task

A machine can now give each task it runs its own short-lived key, a **workload**, whose scope only narrows the machine's: the credentials, tags, projects and modes the task may use. The vault keeps one task out of another's credentials, asks and runs, names the task in the audit and on the pages a person decides on ("Task: <label>, as the machine named it"), and ends its reach when the workload is revoked or expires, or its machine is revoked. A machine may also ask for less than the workspace's default scope when it enrols, down to acting only through workloads. Two refusals are new: `workload_ended` and `workload_required`. A harness creates workloads with `@mehen/client`, which is new too. See [Workloads](concepts/machines.md#workloads) and [One workload per task](guides/harnesses.md#one-workload-per-task).

`mehen workload ls` and `revoke`, and the `mehen enrol` flags that ask for a narrower scope (`--tag`, `--project`, `--mode`, `--no-private`, `--workloads-only`), came with `mehen` 0.3.1; 0.3.0 does not have them.

### 28 October 2026: workspaces

The vault moved to workspaces: one account belongs to any number of workspaces, each with its own members, teams, projects, credentials, machines and audit, at `https://app.mehen.dev/w/<slug>/`. The vault's data started fresh: machines enrolled before, credentials and projects did not carry over, and every machine enrols again in a named workspace with `mehen enrol --workspace <slug>`. The `mehen` release notes below say what changed for each version of the command line.
